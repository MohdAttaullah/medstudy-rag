# Backup, restore and disaster recovery

What must be backed up, what can be rebuilt, and in what order to recover. **No RPO or RTO is
stated**, because none has been measured or approved; inventing one would be the most misleading
number in this repository.

## Authoritative versus rebuildable

The distinction decides the whole strategy: authoritative data is irreplaceable if lost;
rebuildable data can be regenerated from authoritative data at a cost in time.

| Data | Class | Rationale |
|---|---|---|
| Original uploaded documents (object store) | **Authoritative** | The evidence every answer cites. Nothing can reconstruct them. |
| PostgreSQL: documents, versions, jobs, users, tenants | **Authoritative** | Identity, provenance and lineage of everything else |
| PostgreSQL: conversations, verified answers, citations | **Authoritative** | A user's question history cannot be regenerated |
| PostgreSQL: configuration revisions, audit events | **Authoritative** | The immutable record of who changed what |
| PostgreSQL: parses, chunks, embeddings metadata, BM25 postings | Rebuildable | Reproducible from originals by re-running ingestion |
| Qdrant vectors | Rebuildable | Reproducible by re-embedding at pinned model revisions |
| Model weight cache | Rebuildable | Re-provisioned from pinned revisions and checksums |
| Evaluation artifacts (`docs/evals/`) | Rebuildable | Regenerated by `scripts/evaluate_m11.py` |

Qdrant is therefore **not** required to be backed up: it is rebuilt. That is a deliberate choice
and is recorded here so nobody later assumes a Qdrant backup exists. Rebuilding is not free — it
costs a full re-embed of the corpus — so a deployment that cannot tolerate that window should back
it up anyway.

## What to back up

1. **PostgreSQL** — the whole database. It holds both authoritative and rebuildable data; separating
   them at backup time would be error-prone for no real saving.
2. **Object store** — the originals bucket, with versioning enabled if the provider supports it.
3. **Configuration** — the deployment's own secret store and environment definitions, which live
   outside this repository by design.

```bash
# PostgreSQL, consistent single-file dump
pg_dump --format=custom --no-owner "$MEDRAG_DATABASE_URL" > medrag-$(date +%F).dump

# Object store originals
aws s3 sync s3://medical-rag-originals ./originals-$(date +%F) --endpoint-url "$MEDRAG_S3_ENDPOINT"
```

**No scheduler ships with this repository.** The procedure is documented and has been exercised;
automating it is a deployment responsibility.

## Restore

Restore into a **disposable** target first. Never rehearse a restore against a live environment.

```bash
createdb medrag_restore
pg_restore --dbname=medrag_restore --no-owner medrag-2026-09-07.dump
MEDRAG_DATABASE_URL=postgresql+psycopg://…/medrag_restore uv run alembic current
```

Then verify, in this order, that:

1. `alembic current` reports the expected head.
2. Row counts for tenants, documents, document versions and conversations match the source.
3. A sampled document version's `object_key` resolves in the restored object store.
4. A sampled conversation turn still satisfies the verified-answer rule — an answer exists if and
   only if the outcome is `VERIFIED`. The database CHECK constraints enforce this, so a restore
   that violated it would fail to load, but confirming it is what proves the constraint survived.
5. Configuration history is intact and its immutability trigger still present:
   `SELECT tgname FROM pg_trigger WHERE tgname = 'configuration_revision_immutable';`

`scripts/verify_restore.py` performs 1–5 against a restored database and prints a sanitized
report.

## Recovery order

Dependencies determine the order; getting it wrong wastes a rebuild.

1. **PostgreSQL** — everything else references it.
2. **Object store** — originals must exist before any re-parse.
3. **Model cache** — re-provision at the pinned revisions; a checksum mismatch fails readiness.
4. **Qdrant** — recreate collections, then re-embed. Until this completes, retrieval is not ready
   and the API correctly reports itself unready rather than answering from a partial index.
5. **Redis** — no durable state; starting it empty is correct. In-flight jobs are recovered from
   the durable job rows, not from the queue.
6. **API and worker** — start after readiness dependencies are satisfied.

The system fails closed throughout: a partially recovered index makes readiness fail, and no answer
is produced from an incomplete corpus.

## Index rollback

Vector semantics are never mutated in place. A new embedding or chunking configuration produces a
**new** index run that is verified before activation, and the previous active index stays active
until it is. Rolling back is therefore an activation change, not a data repair:

1. Identify the previous verified index run (`GET /api/v1/index-runs/{id}`).
2. Reactivate it through the audited ingestion workflow.
3. Confirm the corpus alignment check passes — retrieval fails closed if the chunk run, dense index
   and sparse index do not describe the same corpus.

Rollback preserves corpus version, index identity, embedding model and revision, and retrieval
policy compatibility, because all four are recorded on the run rather than inferred.

## Configuration rollback

M10 revisions are append-only and immutable. A bad runtime-safe change is undone by **creating a
new revision restoring the prior value**, never by editing history:

1. `GET /api/v1/settings/history` and read `effective_snapshot` from the last good revision.
2. Preview and apply the prior value as a new change.
3. The new revision becomes effective for subsequent requests; in-flight requests keep the snapshot
   they resolved.

A pending rebuild proposal is abandoned the same way — by superseding it with a revision that
restores the previous desired value. Because a proposal never changed the effective configuration,
abandoning one has no effect on what is currently serving.

## What is not implemented

* Automated backup scheduling or retention enforcement.
* Point-in-time recovery (requires WAL archiving at the database layer).
* Cross-region replication.
* An RPO or RTO. None has been measured; none is claimed.
