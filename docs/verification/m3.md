## 4. Chunking architecture

Input is the **active** `ParseRun` only (`is_active`, `SUCCEEDED`, validation `PASS`/
`PASS_WITH_WARNINGS`) and its persisted pages, elements, tables, figures and formulas. The raw
Docling artifact is not a chunking input. `repositories/chunking.load_source` converts rows into
frozen contracts, so the builder can reach neither the database, the parser library nor object
storage.

Boundaries derive only from signals M2 measured as stable — page, reading order, normalized text
and offsets, declared parent links, explicit artifact relations, and bounding boxes for
repeated-margin detection. They never derive from caption/header/footer classification, formula
labelling or list grouping. Full contract: [document chunking](../architecture/document-chunking.md).

## 5. Tokenizer

MedCPT Article Encoder WordPiece, bundled at
`backend/app/ingestion/chunking/assets/medcpt/tokenizer.json` with its LICENSE and manifest.
Revision `d05a736da4bb84ee4057b7f7999485be6ed85465`, file SHA-256
`6e046044df8a2fcedb10607075dca187cae61d806c0d80a96c5b81017edc90c9`, `tokenizers` runtime `0.23.2`.
All three are pinned inside the policy and verified at load; a mismatch raises
`CHUNK_TOKENIZER_LOAD_FAILED` and the run fails closed
(`test_missing_or_tampered_tokenizer_fails_closed`).

It is used **only to count and slice tokens**. No weights are loaded, nothing is downloaded at
runtime, nothing is embedded. Splitting slices *source offsets*; decoded token text is never used
to rebuild source, so capitalization, symbols, units and doses survive
(`test_tokenizer_preserves_source_offsets_and_counts_subwords`).

## 6. Parent/child strategy

Regions are cut at declared ancestry changes and deterministic numbered headings. Units are formed
by preference: section boundary, paragraph, list, sentence, then token slicing only as a fallback.
`TEXT_PARENT` targets 1280 tokens, `TEXT_CHILD`/`LIST` target 384; both are configuration defaults.
Adjacent small children merge only while they stay under the child target. Lists stay with their
heading and split only between whole items; an explicit `term:` label keeps its definition. Parents
and their children share one chunk run, and the database refuses a parent in another run.

## 7. Table strategy

Tables never enter the text splitter. Canonical cells are the source of truth and are stored on the
chunk. A small table is one `TABLE` chunk; a larger one splits into `TABLE_PART` chunks on
row-span-aware groups — a merged row is never cut (`test_merged_rows_are_not_split`). Every part
repeats byte-identical header rows and records its row indexes, header rows, caption and selected
cells. Linked footnotes are attached. A parser-flagged continuation records
`possible_continuation`/`continuation_of_id` and `table_group_id`; parts are **not** merged. An
invalid grid raises `CHUNK_TABLE_FAILED` rather than being repaired
(`test_invalid_table_fails_without_synthetic_repair`).

## 8. Formula strategy

`FORMULA` chunks are atomic and carry the expression exactly as parsed, plus only the neighbouring
elements M2 explicitly linked (bounded by `formula_neighbour_elements`, default 1). No model
interprets, completes or corrects a formula, and no definition is inferred from model knowledge. An
empty expression is a `CHUNK_FORMULA_EMPTY` finding.

## 9. Figure strategy

`FIGURE_CONTEXT` chunks use the source caption, deterministically linked neighbouring text, the
hierarchy and the `FigureArtifact` id. **No visual reasoning and no vision model.** The stored crop
remains the visual source. A figure with no source text is recorded as `visual_only` and surfaces a
warning that says its image remains available, rather than being described.

## 10. Question strategy

Conservative source-pattern extraction produces `QuestionArtifact` rows with number, stem, type
(MCQ, MULTI_SELECT, TRUE_FALSE, SHORT_ANSWER, LONG_ANSWER, UNKNOWN), ordered options, explanation,
page range and the document's authority metadata. **Question and options are one atomic `QUESTION`
chunk**; an explanation stays with it when it fits and otherwise becomes a linked
`QUESTION_EXPLANATION` child that still points at the same question.

`Answer: B` is stored as `B`. **When the source states no answer, `explicit_answer` is NULL and
nothing is inferred** — `answer_inferred` is always false and the `never_infer_answers` check
constraint makes an inferred answer unstorable. Grouping the source did not state is marked
`structure_inferred`; ambiguous option ordering or an empty stem sets `NEEDS_REVIEW` and raises
`CHUNK_QUESTION_BOUNDARIES` instead of guessing. The UI prints “Absent; no answer inferred”.

## 11. Source-coverage policy

Eligible = every element with non-whitespace text, minus the elements excluded as repeated margins
(which remain fully present in the parse run — nothing is deleted). For each eligible element the
union of its mapped span intervals must cover all of its non-whitespace characters.

| Condition | Finding | Severity | Result |
|---|---|---|---|
| Eligible element never mapped | `CHUNK_SOURCE_COVERAGE` | CRITICAL | FAIL |
| Mapped element, text no chunk covers | `CHUNK_SOURCE_TEXT_OMITTED` | CRITICAL | FAIL |
| Text only a `TEXT_PARENT` still covers | `CHUNK_SPLIT_TEXT_OMITTED` | ERROR | NEEDS_REVIEW |
| Whitespace between spans | none | — | — |
| Span offsets out of range or unresolvable | `CHUNK_SOURCE_INVALID` | CRITICAL | FAIL |

Verified positively (all 14 fixtures keep every character even with a 32-token child budget) and
negatively (both detectors fire on deliberately truncated spans). The database independently
refuses a span whose end offset exceeds the element's normalized text.

## 12. Hash and idempotency policy

`chunk_hash` = SHA-256 over version id, parse run id, policy fingerprint, chunk kind, source text,
retrieval text, source spans, artifact ids, hierarchy and metadata. The row UUID
(`uuid5(run_id, chunk_hash)`) is a database key, never semantic identity. Relabelling every element
leaves all chunk hashes unchanged (`test_borderline_labels_do_not_change_chunk_hashes`).

`ChunkRun.policy_fingerprint` = SHA-256 of the whole frozen policy, including the tokenizer pins and
thresholds. `ChunkRun.input_fingerprint` = SHA-256 of the whole normalized input.

Reuse requires **all** of: same active parse run, same policy fingerprint, and a freshly recomputed
input fingerprint equal to the stored one. A forced rechunk always builds a new run and, for
identical input, produces new row ids with identical chunk hashes. Duplicate outbox delivery is
idempotent: the receipt is claimed once, and a run already claimed or superseded is cancelled rather
than rebuilt. One pending-or-running run and one active run per version are enforced by partial
unique indexes.

## 16. Host and container determinism

Two different claims, tested separately.

**Chunking determinism — required, and verified.** The 14 gold fixtures are frozen normalized
inputs, so the same input can be chunked on both platforms. The Windows host and the Linux worker
image produced **byte-identical dataset hashes for all 14 cases**:

```
sections b6a78aa86a19   paragraphs 172b4bdd3691   table 0b10fc4bae9c   large-table 13d65bfc9144
formula fd202ac18736    figure 3565de925790       columns 75904b9bc121  page-transition cebb3b8f0d6c
mcq 654122750104        explanation f471f86db73d  margins 308262427cfd  list 3d405726f73d
footnote 44c9e83e34da   continued-table f23e7c837651
```

Same policy fingerprint `0a91b52d4ace`, same tokenizer revision, 94/94 checks on both.

**Parser determinism — not required, not claimed, and still false.** M2 measured that parsing the
same PDF on Windows and in the Linux container agrees on page counts, page text, table cells, grid
geometry and reading order but disagrees on borderline semantic labels (page header/footer,
caption association, formula detection, list grouping). That is unchanged and is not hidden here:
the parsing gold dataset remains baselined per environment (host 9/9, container 4/9). M3 is built
so those labels cannot decide a boundary or a content hash, which is what makes the identical-input
result above meaningful — it is not evidence that the same PDF yields the same chunks everywhere.

## 17. Known limitations

* Token targets and `ChunkThresholds` are uncalibrated defaults chosen against synthetic fixtures.
  They are bounds on observable counts, not a quality measure, and need re-tuning on a real corpus.
* Whether these are *good retrieval units* is unanswerable until embeddings, an index and retrieval
  evaluation exist. Nothing here measures retrieval or medical accuracy, and no percentage of
  correctness is claimed.
* Question recognition is deliberately conservative single-pattern matching (`1.`/`Question 1.`,
  `A.`–`H.`, `Answer:`, `Explanation:`) over source order. Real question banks use layouts it will
  not recognise; unrecognised material stays as ordinary text rather than becoming a wrong question
  object, and ambiguity routes to review.
* There is no review-approval workflow. A `NEEDS_REVIEW` dataset is rechunked or cancelled, and
  rechunking consumes the bounded retry budget.
* No retention or cleanup of superseded chunk runs; they accumulate for inspection.
* Chunking has a timeout, element and character guards and a lease, but no hard memory sandbox or
  per-tenant quota.
* Worker in-process chunk timing is not scrapeable; the exposed chunk series are derived from
  PostgreSQL at scrape time.
* Cross-page merging relies on the parser's declared structure; a table continuation is flagged and
  left unmerged rather than joined, so a genuinely split table remains two datasets' worth of parts.
* The synthetic fixtures do not represent real medical typography, long reference lists, dense
  multi-column tables or malformed publisher PDFs.
* Local development only: development bearer identities are not production OIDC, there is no AV
  scanning, TLS, managed secrets, backup/retention/purge or installed telemetry pipeline. None of
  this is clinical validation or compliance certification. Production startup remains rejected.
