# M4 verification report

Biomedical embedding generation, versioned vector representations, Qdrant indexing, verified index
activation and embedding/index-quality validation. Date: 2026-09-06.

**Boundary.** Successful jobs now run
`UPLOADED → VALIDATING → QUEUED → PARSING → NORMALIZING → ENRICHING → READY_FOR_CHUNKING →
CHUNKING → VALIDATING_CHUNKS → READY_FOR_EMBEDDING → EMBEDDING → INDEXING → VERIFYING_INDEX →
READY_FOR_RETRIEVAL`.

`READY_FOR_RETRIEVAL` means the vectors were built and the index reconciled point for point, so
this corpus version is *technically eligible* for a later retrieval milestone. **It does not mean
the document is medically answerable.** There is no query encoder, no search, no ranking, no
reranking and no generation. Every version remains database-constrained unsearchable, Ask stays
disabled, and `READY` remains unreachable.

## 3. Pooling, dimensionality and metric

Last hidden state of `[CLS]`; 768 dimensions; no L2 normalization; 512-token maximum; float32 on
CPU. Similarity is inner product (`DOT`), because unnormalized vectors make maximum inner product
the correct metric. The loaded model is cross-checked at load: its `hidden_size` must equal the
configured dimension and its position limit must cover the configured maximum.

Mean pooling and normalization were considered and rejected for M4; either would change what every
stored vector means. See [ADR-009](../adr/009-m4-medcpt-embeddings-and-vector-index.md).

## 4. Embedding-input representation

A deterministic two-field construction matching MedCPT's article representation:

```
field 1  Document title > chapter > section > artifact caption   (compact context)
field 2  the M3 retrieval representation, verbatim               (body)
```

The context is assembled only from persisted facts — the chunk's own `HIERARCHY`-role source
mappings and its artifact caption. Nothing is summarized, paraphrased or invented, and no LLM is
involved anywhere. Over-budget context is trimmed **from the front**, keeping the nearest heading
and caption; the trim is deterministic and inside the hash. An empty context stays an empty first
field rather than being folded into the body.

`ChunkEmbedding.input_hash` is a SHA-256 over the builder version, model id and revision, the
separator and both fields — exactly what the model sees. The embedding input is a derived
representation and never replaces source text; the chain remains
original PDF → parsed element → chunk source text → retrieval representation → embedding input →
vector.

## 5. Truncation policy

`REJECT`, and it is the only policy implemented.

Every input is measured with the model's own tokenizer before inference. Any input over 512 tokens
fails the run with `EMBEDDING_INPUT_TOO_LONG`, persists a CRITICAL finding naming each offending
chunk id and its token count, and **embeds nothing**. `EmbeddingError.details` carries the chunk
ids and marks the error non-retryable, because rechunking is the remedy. The `truncated` column is
constrained to false, so a truncated vector is unstorable even by mistake.

Verified three ways: a unit test on the real encoder with a 698-token fixture, an integration test
that fails the whole run and leaves zero `chunk_embeddings` rows, and the evaluation harness's
`truncation-policy` case.

## 6. Eligible chunk types

Eligible: `TEXT_CHILD`, `LIST`, `TABLE`, `TABLE_PART`, `FORMULA`, `FIGURE_CONTEXT`, `QUESTION`,
`QUESTION_EXPLANATION`, `OTHER_STRUCTURED`.

**`TEXT_PARENT` is excluded and cannot be enabled through configuration** — `embed_parent_chunks`
is `Literal[False]` and a config listing `TEXT_PARENT` fails validation. A parent is the union of
its children, so indexing both would return a whole section where a passage was wanted and would
double-count the same source text in a ranking. Parents remain for later context expansion, where
they would need a separate vector name or an explicit retrieval role.

Question-bank chunks are indexed with `source_type`, `authority_level` and their question status in
the payload, so a later stage can filter or weight assessment material. Being indexed never
promotes a question key to reference authority.

## 7. Qdrant schema

| | |
|---|---|
| Collection | `medrag_chunks_<schema version>_<semantics fingerprint prefix>` — e.g. `medrag_chunks_v1_9f291d23639d` |
| Vector | **named** `medcpt_dense`, 768 dimensions, `DOT` distance |
| Point id | `uuid5(fixed namespace, "{chunk_id}/{vector_name}")` — deterministic, never index-generated |
| Payload | tenant, document, version, chunk run, embedding run, embedding version, index run, chunk, parent chunk, question, chunk type, source type, authority level, subject, specialty, page range, sequence, chunk hash |
| Payload indexes | `tenant_id` (tenant-oriented keyword), `document_id`, `document_version_id`, `chunk_type`, `source_type`, `authority_level`, `embedding_run_id` |
| Alias | `medrag_chunks_active` |

Names were chosen so BM25 sparse and late-interaction vectors can be added to the same points later
without changing point identity. The vector semantics are part of the collection name, so an
incompatible model change builds a new collection beside the old one.

`ensure_schema` refuses to adapt: an existing collection whose vector name, dimension or distance
disagrees raises `VECTOR_SCHEMA_MISMATCH`. Verified directly against the running server.

Chunk text is deliberately **not** in the payload. PostgreSQL is the canonical content store, chunk
ids resolve there, and copying licensed medical bodies into a second system would widen the
exposure surface for no retrieval benefit.

`qdrant-client` is pinned to `>=1.15,<1.16` to match the deployed `qdrant/qdrant:v1.15.4`; the
client refuses a gap larger than one minor.

## 8. Tenant strategy

One shared collection with explicit tenant partitioning, not a collection per user. `tenant_id` is
a keyword payload index marked tenant-oriented, and every server-side query filters it.

Verified at the repository boundary, not in the frontend: with a run's points present, a query for
a different tenant returns `count == 0` and `scroll_ids == ()`, and the API returns 404 for a
cross-tenant caller on every M4 route. Qdrant is unreachable from the browser; the one
live-statistics endpoint is server-side and requires `document:manage`.

## 9. IndexRun activation semantics

```
EmbeddingRun succeeds → IndexRun STAGING → batched upserts → VERIFYING → reconcile → VERIFIED → activate
```

Reconciliation reads the points back and compares them against the expected set recorded in
PostgreSQL: every expected point present, no unexpected point in the run, the vector present under
the configured name, the right dimension, the vector checksum byte-identical to what was computed,
the tenant correct, and the critical provenance payload keys correct.

**Consistency model, stated plainly.** Qdrant gives per-operation acknowledgement, not
multi-operation transactions. A batch of upserts is not atomic across batches and nothing here
pretends otherwise. Correctness rests on deterministic point identity (a replay overwrites),
read-back reconciliation against a durable expected set, and activation as a **PostgreSQL state
change performed only after verification**. PostgreSQL holds the authoritative active-index
pointer; the alias is an operator convenience and a migration tool, and an alias update that fails
is tolerated precisely because it is not authoritative.

Consequences, all tested:

* A failed replacement **leaves the previous active index untouched** — the old collection is never
  deleted first and the new run simply never activates.
* Partial points from a failed load remain tagged with a failed `embedding_run_id`; they are never
  active and never reconciled.
* `active_index_run_verified` allows `is_active` only for a `VERIFIED` run whose indexed and
  verified counts equal its expected count; a trigger additionally refuses activation unless the
  owning embedding run succeeded with zero failures.
* Superseding a chunk dataset (rechunk or reparse) automatically deactivates the embedding and
  index runs built from it.

## 10. Migrations

`m4_embeddings_and_index` (down_revision `m3_hierarchical_chunks`) adds five tables —
`embedding_versions`, `embedding_runs`, `chunk_embeddings`, `index_runs`,
`index_validation_findings` — with their indexes, constraints and triggers; adds
`READY_FOR_RETRIEVAL` to the status vocabulary; replaces the transition guard with the M4 graph
including the re-embed edge; adds `embedding_run_id` to `outbox_messages`; and adds the
`uq_chunk_runs_id_version_tenant` composite key the new foreign keys need.

`READY_FOR_RETRIEVAL` is 19 characters — exactly the width `READY_FOR_EMBEDDING` already forced — so
only the CHECK constraint changes. That matters: M3 attached triggers to `ingestion_jobs.status`,
and PostgreSQL refuses to alter the type of a column a trigger definition depends on. Two ordering
defects found and fixed during verification: the composite unique key must be created before the
table that references it, and dropped after it.

The downgrade **refuses to run while any row still holds an M4-only status**, rather than silently
rewriting it. Demonstrated, not assumed:

```
alembic downgrade m3_hierarchical_chunks
  → psycopg.errors.RaiseException: Cancel M4 jobs before downgrading; no states are silently rewritten
```

After performing the prescribed operator action (cancelling the one `READY_FOR_RETRIEVAL` job
through the real guard), `downgrade → current → upgrade → check` completed with
**No new upgrade operations detected**. `create_all()` is not used anywhere.

## 14. Host and container numerical comparison

`scripts/compare_embedding_environments.py`, 11 fixed synthetic inputs, emitted on the Windows host
and inside the canonical Linux worker image, then compared:

| | |
|---|---|
| Model revision, weight checksum, tokenizer revision, semantics fingerprint | **identical** |
| torch | `2.14.0` (host) vs `2.14.0+cpu` (worker); transformers, tokenizers, safetensors, numpy identical |
| Input hashes | identical for all 11 — the two runs embedded exactly the same text |
| **Byte-identical vectors** | **0 / 11** |
| Worst max abs delta | **9.537e-07** |
| Worst cosine agreement | **1.000000000** |
| Ranking agreement | **11 / 11** anchors order every other fixture identically |

Stated precisely, and not overstated:

* **Same host, same batch layout, repeated** — byte identical. Asserted.
* **Batched versus single inference on one host** — numerically equivalent, not byte identical
  (padding changes the last bits). Asserted with a tolerance.
* **Host versus container** — numerically equivalent to within 1e-6 with identical similarity
  ordering, but **not** bit identical. Measured, reported, and deliberately not asserted as
  equality anywhere in the test suite.

Consequently `vector_checksum` is a **byte identity for storage integrity** — it proves the index
returned what was computed — and never a claim of cross-machine reproducibility or of embedding
quality. Vector *reuse* keys on `input_hash` and the embedding version, never on a checksum.

**The canonical stored corpus embeddings are the ones produced by the Linux worker**, which is the
only environment that writes to the real index.

## 15. Offline model operation

`scripts/provision_embedding_model.py` downloads exactly the pinned revision, verifies the weight
checksum and writes a manifest. It is the only step that reaches the network. The worker mounts the
`embedding-models` named volume at `/home/medrag/models/embeddings` and runs with
`MEDRAG_EMBEDDING__OFFLINE=true`; a model absent from that cache fails closed with
`EMBEDDING_MODEL_UNAVAILABLE_OFFLINE` rather than reaching out. Verified by provisioning a clean
volume from the worker image as uid 10001 and then running the full smoke with downloads disabled.

This is deliberately stricter than the M2 parser, whose weights are still fetched on first use.

## 16. Known limitations

* **Retrieval quality is entirely unmeasured.** Whether these vectors retrieve well is unanswerable
  until a query encoder, a search path and a gold retrieval set exist. Nothing here is Recall@K,
  MRR or nDCG, and no percentage of correctness is claimed anywhere.
* The similarity sanity check is two anecdotal pairs and nothing is tuned against it. Because
  MedCPT article vectors are unnormalized, inner products between unrelated passages remain large in
  absolute terms; only ordering is asserted, and the margin on these fixtures is narrow (≈74 vs 67).
* CPU inference at ~1.9 embeddings/second is slow for a real corpus. No GPU path, no quantization
  and no ONNX export exist.
* Peak process memory in the worker is ~1.2 GB with one model loaded; there is no hard memory
  sandbox and no per-tenant embedding quota.
* Resumability is coarse: a crashed run is failed by the lease sweeper and retried as a whole run
  with vector reuse, rather than resuming mid-batch from a checkpoint.
* Orphan points from a failed load are never active but are not garbage-collected; there is no
  retention or cleanup of superseded embedding runs, index runs or collections.
* Per-batch embedding duration and throughput are recorded in run metrics but are not exposed as
  scrapeable histograms, for the same reason as parse and chunk duration.
* The `verify_sample_ratio` setting exists but full verification is always used; sampling has not
  been exercised.
* Qdrant runs as a single unauthenticated local node with no TLS, no API key, no replication and no
  backup. Port 6333 is published for development only.
* Fixtures remain synthetic. They do not represent real medical prose, dense tables or real question
  layouts, and the M2 finding that parser labels vary between CPU environments is unchanged upstream.
* This remains local development: no production OIDC, credential lifecycle, AV scanning, TLS,
  managed secrets, backup/retention/purge or installed telemetry pipeline. None of this is clinical
  validation or compliance certification. Production startup remains rejected.
