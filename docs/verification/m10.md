# M10 verification report

Enterprise configuration administration: a typed registry over the existing M3–M9 policies,
tenant-scoped immutable revisions, and an explicit separation between what a change makes
effective now and what it merely proposes.

**M10 adds no way to weaken the safety chain.** Every gate, verifier and abstention rule that M7
and M8 established is either read-only or tunable only in the stricter direction. The Ask contract
is unchanged: an answer still reaches a reader only after M8 returns PASS.

**Everything measured here used a synthetic corpus written for this repository.** Synthetic
engineering verification is not clinical validation, and none of it is evidence about clinical
performance.

## 4. The compatibility defect that was found and fixed

The interrupted session's final command was declined before it ran. It intended to relax two
cross-field validations in the registry. Only one of the two was a real defect; applying it
wholesale would have introduced a second.

**Correct, and fixed.** M10 refused any state where `evidence_budget.max_tokens_per_block` exceeded
`max_total_tokens`. M6 holds no such relation. `EvidenceBudgetConfig` declares no validator between
the two, and `evidence/assembly.py` applies them independently — a block is refused if it exceeds
either — so a total below the per-block ceiling simply means the total binds first.
`test_m6_units.py:217` constructs exactly that state (`max_total_tokens=4` against the default
1024 per block) and asserts the resulting single block and budget finding. **M10 was rejecting a
configuration that a passing M6 test constructs.** The rule is removed.

**Incorrect, and kept.** The declined patch also proposed removing the `reranking.candidate_top_k`
validation. That rule is not an M10 invention: M5's `RetrievalConfig` validator declares
`final_top_k > dense_top_k + sparse_top_k` invalid, and `services/evidence.py` builds M6's pooling
config by assigning `candidate_top_k` into that field through `model_copy`, **which does not re-run
validators**. Removing the check would have made a state M5 declares invalid reachable through
configuration rather than merely unconstructable. It is kept, and now documented as M5's rule.

The third rule — both fusion weights at zero — is also kept. M5 rejects it only under
`HYBRID_RRF`, but M6 and Ask always search with `mode="HYBRID_RRF"` regardless of the configured
mode, so on the path this surface configures it disables retrieval outright.

Two regression tests now pin both directions: `test_m10_does_not_add_constraints_m6_does_not_hold`
and `test_constraints_m5_does_declare_are_still_enforced`. The principle is recorded in ADR-015: a
configuration surface may not tighten the policy it exposes.

## 5. Persistence, concurrency and history

`configuration_revisions` is append-only and tenant-scoped, storing the complete allowlisted
effective snapshot, runtime overrides, pending desired values, actor, timestamp, correlation id,
reason and per-change old/new values with impact.

* **Optimistic concurrency.** `expected_revision` rejects stale writes with 409. A tenant row lock
  serializes writers, including the first-revision case where no settings head row exists yet. Two
  concurrent first writers produce `[200, 409]`, never two revision 1 rows.
* **Preview tamper protection.** The preview token is a digest over the validated change, the
  server-generated impact, the tenant and the startup identity. Submitting a different value while
  reusing an approval fails with 409, and the server revalidates every mutation regardless.
* **Immutability in the database.** A PostgreSQL trigger rejects `UPDATE` and `DELETE` on
  configuration history; a raw SQL update, a raw delete and a duplicate `(tenant_id, revision)`
  insert each raise, asserted directly against PostgreSQL rather than through the service.
* **Mixed activation.** A revision must contain either runtime changes or rebuild proposals. A
  mixed batch fails with 422 and writes nothing, so one revision always has one activation meaning.

## 7. Effective versus desired

A runtime change activates as one committed revision and applies to *subsequent* requests; a
request in flight keeps the snapshot it resolved. A rebuild-dependent change is stored as a
proposal: `status` becomes `PENDING_REBUILD`, `desired_value` shows the proposal, and
`effective_value` does not move. Verified in three places — the integration suite, a live HTTP
smoke, and the browser.

M10 **does not** dispatch rebuilds, restart services, or mark a proposal active because an
environment value later happens to match. The UI says so in the applied-change message. An
operator must complete the established versioned rechunk/reindex and activation workflow outside
M10. No old and new vector semantics are ever mixed, because no editable setting alters an active
index in place.

## 8. Request policy snapshot

`ControlPlane.for_request` resolves one revision before the pipeline starts and copies every
policy-bearing service. No shared service graph is mutated.

A cache defect found by the interrupted session is verified fixed: a request copy delegates
`encoder()` to the parent's bound method, so the lazy MedCPT encoder loads once on the shared graph
and every later request copy reuses it.
`test_policy_snapshots_reuse_lazy_encoder_and_audit_invalid_bodies` asserts that two independent
`for_request` copies return the identical encoder object and that the factory was called **exactly
once**. Changing tenant policy does not reload a model.

Ask stores the exact allowlisted snapshot — revision, fingerprint and values — with the turn, so a
historical verified answer stays traceable to the policy that produced it. A later revision does
not rewrite an older turn's snapshot. Secrets are not in the snapshot.

## 9. Authorization and tenant isolation

`settings:read` and `settings:write` are **admin only**. Curators and readers hold neither; the
reader role is unchanged from M9.

| Attempt | Result |
|---|---|
| Unauthenticated read | 401 |
| Reader read / preview / write | 403 |
| Foreign-tenant admin reusing a preview | 409, and their history stays empty |
| SYSTEM-scope write (`reranker.batch_size`) | 422 |
| Client supplying `tenant_id`, `scope` or `lifecycle` | 422 (`extra="forbid"`) |

Tenant identity comes from the principal, never a request body. Every read and write filters on the
caller's tenant.

## 10. Safety invariants are not configurable

There is no API or UI path to disable sufficiency, disable verification, allow unverified answers,
stream unverified tokens, disable tenant isolation, treat pretrained knowledge as evidence, or
search partial ingestion. Attempting any of them returns 422:

`ask.requires_verified_pass`, `ask.stream_answer_tokens`, `claim_verification.*`,
`final_verification.*`, `contradiction.*`, `sufficiency.conflict_policy`, `grounding.*`,
`repair.max_attempts`, `repair.may_widen_evidence`, `embedding.truncation_policy`,
`retrieval.degradation_policy`, `chunking.overlap_tokens` and every source-authority entry are all
`IMMUTABLE`.

Defence in depth: `overlay` refuses a non-editable key, and `resolve` independently refuses to
apply any stored key that is not `RUNTIME_SAFE`, failing closed with 503 rather than silently
ignoring it.

**The one nuance worth stating plainly.** The sufficiency thresholds
`sufficiency.<kind>.min_supporting_blocks` and `min_independent_sources` *are* runtime-editable.
Both have a floor of `ge=1` and both already default to `1`, so an administrator can only raise
them. Every reachable change to the gate makes it **stricter**; none can make it more permissive.

Ask safety regression, all verified against the real pipeline:

* A runtime change cannot expose an unverified draft — a verified answer still requires PASS.
* A runtime change cannot bypass the M7 gate; raising `sufficiency.table.min_independent_sources`
  to 9 produces `INSUFFICIENT_EVIDENCE` with **zero provider calls**.
* A runtime change cannot rescue a verifier failure; with the verifier returning UNSUPPORTED the
  outcome is `UNVERIFIED` with no answer, no citations and no sources.
* A legitimate runtime change still allows a normal verified answer.

## 11. Secrets

No credential is editable, and no credential value is returned. `credentials.openai` and
`credentials.anthropic` report **presence only**, as `Configured` / `Not configured`. The settings
response contains no dev token, no database URL, no `api_key` and no `base_url`.

Approved provider/model pairs come only from server startup configuration
(`MEDRAG_APPROVED_MODELS` plus the configured generator and verifier). The browser cannot invent a
provider, model, endpoint or key.

Change reasons cannot smuggle credentials into history: a bounded regex plus exact matching against
the process's real secrets rejects with 422. Rejections are audited by **declared result code
only** — the offending value and key are never echoed into the audit payload, the response or the
logs, which is asserted with a real `sk-`-shaped string.

## 12. Frontend

The Settings workspace renders backend metadata and duplicates no policy classification. It
provides the ten server-returned sections, search, effective value, desired/pending value, a
lifecycle badge, the impact description, backend validation errors, mandatory confirmation, the
approved model registry with credential presence, and paginated immutable history. A reader never
fetches `/settings` at all. Changing a proposed value after previewing invalidates the preview, so
a stale approval cannot be applied.

## 14. Browser

Desktop and 390 px mobile, run against a **drained worker queue**. Both M10 Settings specs pass:
preview → explicit confirmation → apply → the new revision appears in immutable history; the
rebuild proposal shows its external-rebuild impact; safety invariants offer no edit control; a
reader sees "Administrator access required" and receives 403 from the API. The mobile pass asserts
`document.documentElement.scrollWidth <= window.innerWidth` — no horizontal overflow — and captures
both screenshots. The spec restores the original value and refuses to overwrite a concurrent
administrator's revision.

**Queue contention, reported rather than hidden.** A first full run had 16 passed and 1 failed:
`upload.spec.ts` timed out waiting 45 s for worker receipt because the preceding specs had queued
five documents behind a worker running at `MAX_CONCURRENCY=1`. Rerun in isolation against a drained
queue it passed in 10.1 s, and a subsequent full run against a drained queue passed **17/17**. This
is local single-worker contention, not a defect.

## 15. Live configuration → Ask smoke

`scripts/smoke_m10.py`, against the running stack with the configured OpenAI provider and a
synthetic document. Nothing stubbed.

1. Reader is refused settings read, preview and write — 403 on all three.
2. A rebuild-required change (`chunking.child_target_tokens`) commits as `PENDING_REBUILD`; the
   effective value **does not move**; the proposal is then restored.
3. An admin previews and applies a runtime-safe change to `retrieval.rrf_k`, reaching revision 7
   with `rrf_k = 61` effective.
4. A full live question runs M5 → M6 → M7 → real OpenAI generator → real verifier → **VERIFIED**,
   `verified: true`, one citation resolving to **three real source elements with a real region**
   on page 1 of a REFERENCE-authority document, and no reason codes.
5. The original value is restored, refusing to proceed if a concurrent admin had revised the
   tenant meanwhile.

Latency: **25 797 ms** end to end — drafting 3 987 ms, verification 25 724 ms, sufficiency 1 ms,
retrieval and reranking well under 200 ms. Generation and verification dominate, as they have since
M8. **This is not a production SLO**, and no threshold in M10 is calibrated. Generator and verifier
are both `gpt-5.6-sol`, so `verifier_independent` is **false**.

One successful live call proves the integration works, not that the model is clinically reliable.

## 16. A defect in an M8 smoke, found and corrected

`scripts/smoke_m8.py` asserted `data["verified"] is False` unconditionally on the M8 diagnostic
endpoint. That contradicted the rest of the same script, which asserts
`data["verified"] is (answer is not None)` and validates the verified branch in full, and whose own
comment states that `verified: true` is legitimate there. The assertion only ever held because the
formula fixture happened to abstain; when the live verifier passed its claims, the smoke failed
while nothing was actually wrong.

`answering_enabled is False` — the real invariant, pinned `Literal[False]` by type — is still
asserted, and the verified/answer relationship is still fully checked. No safety check was removed
or weakened. The same pattern in `smoke_m7.py` is correct and was left alone, because
`DraftResponse.verified` genuinely is `Literal[False]`.

## 17. Known limitations

* **Synthetic engineering verification is not clinical validation.** No clinician reviewed any of
  this corpus, and nothing here measures medical quality.
* The verifier is the same model as the generator, so verification is not independent.
* Latency is provider-dominated and uncalibrated. No M10 threshold is a measured value.
* M10 creates rebuild **proposals** only. There is no automated rebuild, reconciliation or
  activation, and desired-value equality is never treated as activation evidence.
* Restart-required and system-scope settings describe the API's startup contract. M10 cannot
  attest to a remote process's actual deployed state.
* Sufficiency minimums are runtime-editable upward only; they cannot be lowered below their
  shipped default of 1, which is also their floor.
* The development RBAC has no system-operator role, so shared service configuration is read-only
  rather than administrable by anyone.
* Three `QUEUED` ingestion rows predate this work; they are orphans from the worker being killed
  to free memory during regression, the queues are empty, and nothing re-dispatches them.
* Playwright's pinned browser build had to be installed manually from Google's official
  chrome-for-testing artifact, because Playwright's own download host returns
  `400 GatewayExceptionResponse` from this network. The binary is the exact official build
  Playwright requires (`153.0.8010.12`, revision 1243); no version was substituted.

## 18. Boundary

M10 ends at safe enterprise configuration. **M11 was not started**: no evaluation framework, no new
datasets, no clinical benchmarking, no model bake-offs, no BGE-M3, no ColBERT, no DeepSeek
experiments and no new retrieval lanes. M12 was not started.

The M9 verified-answer safety chain is intact: `AskResponse` still carries an answer if and only if
the outcome is `VERIFIED`, the same rule still holds on the stored-turn view, and the two database
CHECK constraints still enforce it underneath. The M9 suite passes unchanged at 64.
