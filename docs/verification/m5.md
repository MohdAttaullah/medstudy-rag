# M5 verification report

Biomedical hybrid retrieval: MedCPT Query Encoder, PostgreSQL BM25, Reciprocal Rank Fusion,
fail-closed corpus alignment, and a measured retrieval baseline.

**What RETRIEVAL_READY means.** Both retrieval lanes verified over the same chunk dataset, so this
corpus version can take part in hybrid retrieval and its candidates resolve to real sources. It
does **not** mean the corpus is medically answerable. No reranking, context expansion, evidence
sufficiency gate, grounding or generation exists. `READY` remains unreachable, every document
version stays database-constrained unsearchable, Ask is disabled, and every retrieval response
carries `answering_enabled: false`.

**Every retrieval number below was measured over a synthetic corpus written for this repository.**
It is not licensed medical content, it has not been reviewed by a clinician, and none of it is
evidence about clinical performance.

because a mismatch would otherwise surface as a plausible-looking but meaningless ranking.

## 3. Query representation and limits

The released query usage encodes a single text field at 64 tokens and reads the `[CLS]` position;
that is reproduced exactly. There is no instruction prefix, no mean pooling, no normalization.

Query preparation is deterministic and mechanical: NFKC, control-character removal, typographic
punctuation folded to ASCII, whitespace collapsed. Clinically meaningful characters survive
verbatim — `Na+/K+-ATPase`, `HbA1c >= 7.5%`, `1.5 mg/kg` all pass through unchanged, asserted by
test. Case is preserved, because the encoder wants the original case.

There is **no LLM query rewriting, no HyDE, no paraphrase, no alternate-query generation and no
synonym or abbreviation expansion.** `SparseAnalyzerConfig.expansion` is `Literal["NONE"]` and a
database CHECK constraint (`sparse_no_uncontrolled_expansion`) refuses any other value, so an
expansion lane cannot be introduced without a deliberate migration.

Truncation policy is `REJECT`. A question longer than 64 tokens raises `QUERY_TOO_LONG` carrying
the limit and the observed count; nothing is shortened. Measured: the gold `q-over-limit` case is
76 tokens against the 64-token limit and is rejected, on both host and Linux.

An in-process query-vector cache is keyed by the encoder's semantics fingerprint plus a hash of
the normalized question. It stores no query text, is never persisted, and cannot serve a vector
across encoder versions.

## 4. Dense retrieval

Dense search runs against the M4 `medcpt_dense` named vector. The corpus is resolved from
PostgreSQL — never from the Qdrant `medrag_chunks_active` alias, which records what an operator
last activated rather than what is verified and version-aligned for this tenant. The search filter
is `tenant_id = <principal>` AND `embedding_run_id IN (<active verified runs>)`, both applied
inside Qdrant. A staged, failed or superseded run's points remain in the collection and are simply
not selectable. `QdrantVectorIndex.search` refuses an unfiltered search outright.

## 5. Lexical retrieval (BM25)

Okapi BM25 with the Lucene inverse document frequency:

```
idf(t)   = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
score(d) = SUM over query terms t of
           idf(t) * (tf(t,d) * (k1 + 1)) / (tf(t,d) + k1 * (1 - b + b * len(d) / avgdl))
```

The Lucene idf form is used because it is never negative; the classical Robertson form penalises a
document for containing a term that appears in more than half the corpus, which is a poor property
for a recall-first first stage. Both formulas are asserted against hand-computed values in
`test_m5_units.py`.

The lexical index lives in PostgreSQL rather than as a second Qdrant vector. That is a deliberate
choice with three consequences: `N`, `df` and `avgdl` are computed over exactly the corpus a query
may see — one tenant's active, verified, version-aligned indexes, never another tenant's data or a
superseded run; the analyzer is ours and versioned, so a term means the same thing at index time
and query time; and `k1`/`b` are **runtime-safe**, because postings store raw term frequencies and
document lengths rather than pre-weighted scores.

Parameters measured at: `k1 = 1.2`, `b = 0.75`. Conventional starting values, benchmarked rather
than assumed; the sweep results are in §11.

### Analyzer

Analyzer `medrag-biomedical` v1, fingerprint `2a53fbfe5239…`. NFKC, case policy
`NORMALIZED_AND_EXACT`, compound policy `WHOLE_AND_PARTS`, **stopwords empty**, term length 1–64,
expansion `NONE`.

Identifiers survive tokenization, which is the whole reason this lane exists. Measured:

| Input | Terms produced |
|---|---|
| `HLA-B27` | `hla-b27`, `hla`, `b27`, `^HLA-B27` |
| `CYP3A4` | `cyp3a4`, `^CYP3A4` |
| `Na+/K+-ATPase` | `na+/k+-atpase`, `na`, `atpase`, `^Na+/K+-ATPase` |
| `HbA1c` | `hba1c`, `^HbA1c` |
| `IL-6` | `il-6`, `il`, `^IL-6` |
| `HER2/neu` | `her2/neu`, `her2`, `neu`, `^HER2/neu` |
| `25-hydroxyvitamin` | `25-hydroxyvitamin`, `25`, `hydroxyvitamin` |
| `1.5 mg/kg` | `1.5`, `mg/kg`, `mg`, `kg` |
| `7.5%` | `7.5%` |

A `^`-prefixed term is the case-exact form, emitted only when the token carries uppercase. It
occupies its own key space, so an exactly-cased identifier match is a rarer and therefore
higher-IDF signal without any hand-tuned boost. Single-character fragments are dropped: a bare `6`
from `IL-6` would match almost every numeric passage.

Stopwords are disabled by default and deliberately: a medical question is short, and discarding
its ordinary words discards the relationships that distinguish two similar questions.

### Sparse index versioning and lifecycle

`READY_FOR_RETRIEVAL → SPARSE_INDEXING → VERIFYING_SPARSE_INDEX → RETRIEVAL_READY`, driven by the
existing transactional outbox with a `SPARSE_INDEX` message kind and a fenced lease.

The corpus is **not** re-derived from eligibility rules. It is taken from the active successful
embedding run's recorded `chunk_embeddings`, so both lanes cover exactly the same chunks by
construction — and verification proves it rather than assuming it. `TEXT_PARENT` is excluded from
both lanes. Reconciliation checks chunk identity both ways, counts, tenant, chunk-run lineage,
chunk type, orphan postings, and that the `sparse_terms` aggregates equal a recomputation from
`sparse_postings` — because query-time IDF reads that aggregate, and if the two disagreed every
score in the index would come from statistics describing a different corpus.

Activation supersedes the previous active index and activates the new one in one PostgreSQL
transaction. A failed replacement leaves the previous active index untouched
(`test_a_second_build_supersedes_the_first_without_deleting_its_history`,
`test_a_lexical_index_cannot_be_built_without_a_verified_dense_index`). Completed indexes are
immutable at the database, their activation timestamp is written once, and their only permitted
status move is `VERIFIED → SUPERSEDED`. Findings are append-only. Superseding a chunk dataset
automatically deactivates the sparse index built from it.

## 6. Fusion

```
score(d) = SUM over lanes i of  weight_i / (k + rank_i(d))
```

Measured at `k = 60`, `dense_weight = 1.0`, `sparse_weight = 1.0` — plain, unweighted RRF as the
production default. Ties break by chunk id so a ranking is reproducible across runs, processes and
machines.

Fusion is rank-based on purpose. A MedCPT inner product and a BM25 sum are numbers on unrelated
scales; adding them would let whichever lane happens to produce larger magnitudes dominate for
reasons unrelated to evidence. Raw lane scores are carried through as diagnostics and are never
combined arithmetically. Score-normalised or learned fusion is deliberately absent rather than
approximated.

Modes: `DENSE_ONLY`, `BM25_ONLY`, `HYBRID_RRF`. A `BM25_ONLY` query performs no model call at all
(`test_dense_only_and_bm25_only_modes_use_exactly_one_lane` asserts the encoder is not invoked).

## 7. Corpus alignment (fail-closed)

A document version is searchable only when **all** of the following hold: its job reached
`RETRIEVAL_READY`; it has an active `VERIFIED` dense index run; it has an active `VERIFIED` sparse
index; both were built from the same `chunk_run_id`; and the document is not archived.

A version still being embedded or reindexed is simply not in the corpus — that is incompleteness,
not inconsistency. A version whose two lanes disagree about the chunk dataset fails the **whole
query** with `RETRIEVAL_CORPUS_MISALIGNED`, proven by
`test_a_lane_disagreement_about_the_chunk_dataset_fails_closed`. Mixed embedding versions or mixed
analyzer versions across the corpus also fail closed, because one query vector cannot search two
vector spaces and scores across them would be meaningless.

The analyzer the active index was *actually built with* is read back and compared with the
configured one; a mismatch raises `SPARSE_INDEX_VERSION_MISMATCH` rather than silently producing
terms the postings do not contain
(`test_an_analyzer_change_is_refused_until_the_lexical_index_is_rebuilt`).

When the configured hybrid strategy cannot run, the default `degradation_policy = FAIL_CLOSED`
fails the request. `ALLOW_DENSE_ONLY` exists but must be configured explicitly and reports
`SPARSE_LANE_UNAVAILABLE_DEGRADED_TO_DENSE` in the response warnings, so a query never quietly
becomes a different retrieval architecture.

## 8. Tenant safety

Tenant comes from the authenticated principal and never from a request body; `SearchRequest`
forbids extra fields, and `test_the_search_body_cannot_carry_a_tenant` asserts a 422. Both lanes
are scoped server-side — Qdrant filters on `tenant_id` inside the engine, and the lexical query
asserts `SparseDocument.tenant_id` explicitly rather than relying on the index scope implying it.
Hydration re-scopes every candidate against the tenant and the resolved corpus, so an identifier
is never trusted merely because it came from our own index. `/retrieval/search` requires
`retrieval:search`, which readers do not hold (403 asserted).

## 9. Migrations

Revision `m5_hybrid_retrieval`, down-revision `m4_embeddings_and_index`. Adds

an append-only trigger on the findings table.

### Negative cases and score separation

Neither negative query has an answer in the corpus, and recall is undefined for them, so they are
scored separately and never averaged in.

| Lane | positive min | positive mean | negative max | negative mean | separable |
|---|---|---|---|---|---|
| Dense | 59.9289 | 65.5983 | 54.6166 | 51.4811 | yes, margin ~9% |
| BM25 | 5.7807 | 20.8940 | 4.4033 | 4.2560 | yes |
| Hybrid RRF | 0.0313 | 0.0327 | 0.0317 | 0.0315 | **no** |

The hybrid row is the important finding. **An RRF score carries no absolute relevance
information**: it is bounded by the constant and the lane count, and here a negative query's top
fused score (0.031746) sits *above* the weakest positive one (0.031319). A later evidence
sufficiency gate must therefore never be built on the fused score. The lane scores do separate on
this dataset, but on 22 positives and 2 negatives that is an observation, not a calibrated
threshold, and no threshold is drawn anywhere in the code.

### Query boundary

| Case | Encoder | Tokens / limit | Dense | Hybrid | BM25 | BM25 candidates |
|---|---|---|---|---|---|---|
| `q-over-limit` | `QUERY_TOO_LONG` as expected | 76 / 64 | unavailable | unavailable | available | 40 |

The encoder's token limit bounds the dense and hybrid lanes only. BM25 never sees the encoder, so
a question too long to encode still ranks lexically from its 58 analyzed terms. Reporting such a
case as a whole-system failure would misdescribe the system.

### Failure analysis

No gold case failed to retrieve its evidence within the fused candidate budget, so the failure
table is empty. The classifier (`LEXICAL_MISMATCH`, `SEMANTIC_MISMATCH`, `BOTH_LANES_MISSED`,
`FUSION_DISPLACED`, `CORPUS_LACKS_EVIDENCE`) is exercised by unit tests rather than by a real
failure. An empty failure table on an 83-chunk synthetic corpus is a statement about the corpus,
not a statement about retrieval quality.

Per-query diagnostics for all 24 scored and negative cases — each lane's rank for each expected
chunk, top scores and candidate counts — are in `.local/m5-retrieval-{host,linux}.json`.

## 12. Performance

Measured, not an SLA, on this corpus with the stated configuration.

| Lane | host p50 | host p95 | Linux p50 | Linux p95 |
|---|---|---|---|---|
| Dense (encode + exhaustive search) | 55.3 ms | 130.7 ms | 54.6 ms | 75.2 ms |
| BM25 | 7.9 ms | 17.1 ms | 7.2 ms | 10.1 ms |
| Hybrid RRF | 65.5 ms | 145.9 ms | 63.0 ms | 85.1 ms |

Cold encoder load 18.9 s (host) / 21.1 s (Linux); corpus embedding of 83 chunks 9.3 s / 9.6 s.
Vocabulary 1,474 terms over 3,142 postings. Dense latency is dominated by the query forward pass
on CPU, which is why a warm process matters and why the encoder lives in a long-lived service.

The harness's dense lane is an exhaustive dot product over the fixture, not an approximate index;
that is deliberate, so the measurement describes the representation rather than folding an index's
own recall loss into it. Production dense latency is Qdrant's and is measured per request in the
retrieval trace instead.

### Warm versus cold, measured on the live stack

`scripts/smoke_m5.py` issues the three modes in order against the running containers, and the
retrieval trace records each stage. The first call pays the query service's cold cost:

| Call | Mode | Total | encoding | dense | sparse | fusion | hydration |
|---|---|---|---|---|---|---|---|
| 1st (cold) | `DENSE_ONLY` | 2667.1 ms | **2578.5 ms** | 56.9 | — | 0.1 | 22.5 |
| 2nd | `BM25_ONLY` | 32.7 ms | **none** | — | 17.4 | 0.0 | 8.2 |
| 3rd (warm) | `HYBRID_RRF` | 46.5 ms | 15.6 ms | 4.5 | 8.4 | 0.2 | 11.3 |

Two things worth stating plainly. The cold penalty is entirely in query encoding — 2.58 s of a
2.67 s request — which is exactly why the encoder lives in a long-lived service rather than being
constructed per request. And `BM25_ONLY` shows **no encoding stage at all**, which is the live
confirmation that the lexical lane never touches the query encoder.

## 16. Known limitations

**Retrieval quality is measured only on a synthetic corpus.** 83 chunks, 22 positive cases. Recall
at depth 10 and 20 saturates for structural reasons. The corpus cannot calibrate candidate
budgets, the RRF constant or the fusion weights, and it cannot support a claim about clinical
retrieval performance. A licensed, de-identified, clinician-reviewed corpus is required before any
of these numbers means anything about real use.

**The fused RRF score is not a relevance signal** and must not be used as an evidence-sufficiency
threshold; measured above.

**Question-bank and answer-key material is retrievable and stays labelled.** M5 returns source
type and authority level with every candidate and does not resolve conflicts, rank by authority or
penalise assessment material. The `q-authority-conflict` case retrieves both the guideline and the
contradicting course handout; deciding between them is M7's problem, and nothing here pretends
otherwise.

**The abbreviation case passes without an expansion list**, because the dense lane carries it.
That is a property of this corpus, not proof that abbreviations are handled in general.

**Lexical scale.** BM25 loads bounded postings into Python and scores them there. It is correct
and deterministic, and it is a development baseline, not an internet-scale lexical engine. A query
whose terms exceed `max_scanned_postings` (500,000) is refused rather than silently truncated.

**Mixed embedding or analyzer versions across a tenant's corpus fail closed** rather than being
searched per-collection and merged. Re-embedding onto one version is the prescribed remedy.

**No approximate-search tuning.** Qdrant HNSW parameters are defaults and unmeasured.

**Dense latency is CPU-bound**; there is no GPU, quantization or ONNX path.

Parsing, chunking and embedding limitations from M2–M4 are unchanged, including the measured
parser-label variation between CPU environments. This remains local development. It is not
clinical validation or compliance certification, and production startup is still explicitly
rejected.
