# Chunk construction evaluation

This measures one narrow question: **did the chunker preserve the structure that was present in its
input?** What it kept together, what it kept apart, what it carried forward verbatim, and what it
never invented.

It is not retrieval evaluation and not RAG evaluation. There is no query, no index, no ranking, no
judge model and no Recall@K here — nothing is retrievable at this milestone, so those numbers would
be meaningless. It is also not a medical accuracy measure: the fixtures are synthetic structures
with invented content, so a perfect score says the chunker is faithful to its input, never that the
input is clinically correct.

It is separate from [parsing evaluation](parsing-evaluation.md), which asks whether the parser
recovered the document, and from [retrieval evaluation](retrieval-evaluation.md) and
[answer evaluation](answer-evaluation.md), which remain unimplemented.

## Dataset

`backend/tests/fixtures/chunking/gold.json` (schema `chunk-gold-m3-v1`), generated by
`scripts/create_chunk_fixtures.py`. Each case is a **frozen normalized parse dataset** with fixed
UUIDs — pages, elements, reading order, bounding boxes and artifacts — not a PDF. Nothing is parsed
at evaluation time, so the harness is fully offline and independent of the parser's environment
variability. Every fixture is original synthetic content: no copyrighted textbook, question bank or
guideline text, and no wording intended to be medically meaningful.

| Case | What it exercises |
|---|---|
| sections | Declared ancestry and numbered headings as region boundaries |
| paragraphs | Parent/child construction and complete source coverage |
| table | A small table staying whole with its caption and cells |
| large-table | Row-group splitting with identical repeated headers |
| formula | An atomic formula chunk with only linked neighbouring context |
| figure | Figure context from caption and linked text, with no visual reasoning |
| columns | Reading-order preservation across a two-column layout |
| page-transition | A unit that legitimately spans a page break |
| mcq | Question and options atomic, explicit `Answer:` preserved |
| explanation | Explanation kept with, or linked to, its question |
| margins | Repeated running head/foot excluded from chunking, not deleted |
| list | List heading kept with its items; splitting only between whole items |
| footnote | A footnote attached to the statement it qualifies |
| continued-table | A flagged continuation kept as two artifacts, never merged |

Cases declare minimum chunk counts by type, required and forbidden text, ordered fragments,
elements that must not be merged, question counts, expected explicit answers, option atomicity,
table-header retention, artifact separation, cross-page behaviour, excluded-element counts and
whether all source text must be mapped. Every case additionally asserts that validation passes,
that the run is reproducible, and that a second build of the same input yields identical chunk
hashes and an identical input fingerprint.

## Running it

```powershell
uv run python scripts/evaluate_chunking.py
```

It loads only the bundled pinned MedCPT tokenizer — no weights, no network — and prints the chunker
version, the policy version and fingerprint, the tokenizer revision, per-case chunk counts and
dataset hashes, and every failure. It exits non-zero on any failure, so a chunker or policy change
that drops source text, splits a question from its options or destabilises chunk identity is visible
instead of absorbed.

## Determinism: what is and is not claimed

* **Claimed and tested.** Identical normalized input + identical chunk policy + identical tokenizer
  produce identical boundaries, source mappings, retrieval text, hierarchy and chunk hashes. This
  holds on the Windows host and inside the Linux worker container alike, because the input is a
  frozen fixture rather than a fresh parse.
* **Not claimed.** That parsing the same PDF on two environments yields the same normalized input.
  M2 measured that it does not, for borderline semantic labels; see
  [parsing evaluation](parsing-evaluation.md). Chunking is deliberately built so those labels do not
  decide boundaries or content identity, but the upstream difference is real and is not hidden here.

## What this does not establish

Nothing here is clinical validation, and no accuracy percentage should be quoted from this harness.
Synthetic fixtures do not represent real medical typography, long reference lists, dense multi-column
tables or the ways a real question bank is laid out. The token targets and `ChunkThresholds`
defaults were chosen against these fixtures and need re-tuning against a real corpus. Whether these
chunks are *good retrieval units* is unanswerable until embeddings, an index and a retrieval
evaluation exist.
