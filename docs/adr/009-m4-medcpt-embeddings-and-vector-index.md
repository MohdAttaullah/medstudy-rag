# ADR-009: MedCPT article embeddings, named dense vectors and verified index activation

Status: Accepted; implemented in M4. Date: 2026-09-06. See
[embeddings](../architecture/embeddings.md), [vector index](../architecture/vector-index.md) and
[the M4 report](../verification/m4.md).

## Representation

Use the released MedCPT Article Encoder for document-side vectors, at a pinned revision with a
verified weight checksum, and reproduce its published semantics exactly: the last hidden state of
`[CLS]`, 768 dimensions, a 512-token maximum, no L2 normalization. Because vectors are
unnormalized, similarity is maximum inner product, so collections are created with `DOT` distance.

Rejected: mean pooling and L2 normalization. Both are common defaults and both would change what
every stored vector means, invalidating comparisons with the published model and with any earlier
run. Either may be adopted later, but only with a benchmark, a new `EmbeddingVersion` and an
amendment here.

Embedding inputs are a deterministic two-field construction — compact declared hierarchy, then the
M3 retrieval representation verbatim — hashed in full. No model writes, summarizes or expands the
input, and the derived input never replaces source text in the provenance chain.

## Truncation

The policy is REJECT, and it is the only policy implemented. An input over the model maximum fails
the run with a finding naming the chunk, and nothing is embedded. Silent truncation is refused
because it would index a chunk whose vector represents only part of the evidence the chunk claims
to carry; a later citation would then point at text the vector never saw. The remedy is to rechunk.

## Eligibility

Only precise retrieval units are indexed. `TEXT_PARENT` is excluded and cannot be enabled by
configuration: a parent is the union of its children, so indexing both would return a whole section
where a passage was wanted and would double-count the same source text. Parents remain available
for context expansion later, and would need a separate vector name or an explicit retrieval role.

Question-bank chunks are indexed but keep `source_type`, `authority_level` and their explicit-answer
status in the payload. Being indexed never promotes a question key to reference authority.

## Index structure

One shared collection per vector space, named for the schema version and the semantics fingerprint,
with **named vectors** from the start (`medcpt_dense`). Sparse and late-interaction vectors are
added to the same points in later milestones without changing point identity. Point ids are
`uuid5(namespace, chunk_id/vector_name)` — derived from application identity, never generated by
the index — so a replayed batch overwrites rather than duplicating.

Payload carries routing, filtering and provenance only. Chunk text stays in PostgreSQL: duplicating
licensed medical bodies into a second store would widen the exposure surface for no retrieval
benefit, since chunk ids resolve there anyway.

Tenancy is a shared collection with an indexed, tenant-oriented `tenant_id` payload key and
server-side filtering, not a collection per user. Rejected: physical isolation per tenant, which
multiplies collection overhead at this scale; it remains available behind a future ADR.

## Activation and consistency

Qdrant provides per-operation acknowledgement, not multi-operation transactions, and this design
does not pretend otherwise. Correctness comes from deterministic point identity, read-back
reconciliation against an expected set recorded in PostgreSQL, and activation as a PostgreSQL state
change that happens only after reconciliation. PostgreSQL holds the authoritative active-index
pointer; the collection alias is an operator convenience and a migration tool, not the source of
truth.

A failed replacement therefore leaves the previous active index untouched — the old collection is
never deleted first and the new run simply never activates. Superseding a chunk dataset
automatically deactivates the embedding and index runs built from it.

## Verification vocabulary

Index findings describe structural integrity: dimension, finiteness, zero vectors, checksum
agreement, missing or unexpected points, payload and tenant agreement, count mismatch. None of them
is a semantic or medical accuracy measure and none may be reported as one.

## Boundary

M4 ends at `READY_FOR_RETRIEVAL`, which means the vectors verified and this corpus version is
technically eligible for a later retrieval milestone. It does not mean the document is answerable.
`READY` stays unreachable in both the application graph and the database guard until query
retrieval, grounding and verification exist.
