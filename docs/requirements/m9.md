## Purpose and the display rule

M9 connects the verified pipeline to the end user. The runtime path stays: question → authorization
and tenant scope → M5 hybrid retrieval → M6 reranking → bounded EvidenceSet → M7 sufficiency gate →
SUFFICIENT only → M7 grounded draft → M8 claim verification → PASS only → VerifiedAnswer → Ask UI.
M9 must bypass no earlier stage.

A user may see a substantive generated medical answer only when M7 is SUFFICIENT, M8 is PASS and
`verified = true`. Anything else must not render as a normal answer; an M7 draft is never displayed
and `UNVERIFIED_AWAITING_CLAIM_VERIFICATION` is never presented as final.

The UI must support at least verified answer, insufficient evidence, conflicting evidence,
verification failure/abstention and system/provider failure as visually and semantically distinct
states. Do not collapse every non-answer into a generic error: the user should understand whether
evidence was missing, evidence conflicted, verification rejected the draft, or the infrastructure
failed — without revealing sensitive internals.

Do not display fabricated confidence, accuracy or score percentages. Meaningful categorical states
such as "verified against retrieved sources", "insufficient evidence", "conflicting source
evidence" or "unable to verify answer" are acceptable; invented probabilities are not.

## Ask page, submission and orchestration

Implement the real Ask page on the established React/TypeScript/TanStack Query architecture, with
question input, submit behaviour, loading and progress state, verified answer rendering, citations,
a source list, abstention, insufficient-evidence and conflict states, source inspection and safe
retry. Keep it focused on educational corpus QA; add no patient-specific diagnostic workflow.

The client sends only the question and legitimate user-controlled filters. The browser must not
supply tenant id, arbitrary EvidenceBlock ids, `verified=true`, source-authority overrides, a
sufficiency result, a claim verification result, a provider key or a provider prompt. Tenant and
corpus identity remain server-owned, and client-supplied verification state is never trusted.

Create or reuse one authorized Ask orchestration service invoking the existing M5→M8 pipeline. Do
not duplicate retrieval or generation logic in API routes, and do not duplicate M7/M8 decisions in
the frontend. The backend owns retrieval, reranking, EvidenceSet construction, sufficiency,
generation, verification and the final display decision; the frontend renders the typed result.

Define a typed public Ask response distinguishing verified answer, insufficient evidence,
conflicting evidence, abstention and failure results. A verified result may carry the answer,
`verified = true`, citations, sources, claim references where appropriate and a correlation
identifier, without unnecessary raw provider internals. Avoid dangerous contracts that return a
draft answer inside a failure object; authorized inspector routes may expose M7/M8 intermediates,
but the public response must not make an unverified draft available for presentation.

## Conversations, history and authorization

Implement the conversation experience if the architecture requires persistence, supporting at least
conversation, question, final outcome, verified answer when PASS, citations and source links, and
timestamps. Decide carefully what must be persisted; do not automatically store raw provider
prompts, credentials, full provider responses, temporary EvidenceSets or internal reasoning. Unlike
M6–M8, M9 may legitimately need persistence: if new relational entities are genuinely required,
create a real Alembic migration, and do not create empty ones.

Every conversation must be tenant- and user-scoped server-side. A user must not read another
tenant's conversation, continue another user's conversation, or fetch another tenant's sources or
citations. Test IDOR-style access explicitly and do not derive authorization from browser route ids
alone. Persisted history must distinguish verified answers from abstentions, insufficient evidence,
conflicts and system failures; never retrospectively store a failed draft as a verified answer, and
where an M8 repair occurred persist and display only the final verified answer.

The complete Ask path must enforce authentication, tenant scope, corpus and source scope,
conversation ownership, and document, citation, source-page and artifact authorization server-side.
Test cross-tenant attempts and fail closed.

## Citations, sources and viewers

Every displayed substantive claim must resolve to approved evidence. M8 already verified citation
identity; M9's job is to render those verified citations accurately, resolving citation →
EvidenceBlock → chunk → element → page → document version → document → original PDF. Do not invent
source labels in the frontend.

A citation should expose useful available metadata — title, page, source type, edition or year,
authority, section, and table, figure or formula identity — without overwhelming the answer;
detailed provenance belongs in a source or evidence panel. The source list must correspond only to
evidence actually supporting the verified answer, keeping diagnostic M5/M6 candidates in authorized
debug views.

Implement source-page navigation so a citation opens the authoritative page, using the original
uploaded source or canonical persisted artifact, revalidating authorization server-side and never
handing the client arbitrary object-store URLs. Where M2 provenance contains bounding boxes,
highlight the region, degrade gracefully when none exists, and fabricate no geometry.

Table-derived citations need a meaningful inspection experience built on the canonical table
representation, preserving headers, rows, cells, footnotes, source page and artifact identity rather
than showing flattened retrieval text as though it were the original. Formula evidence must display
the exact authoritative source expression, with source-provided definitions where available and no
frontend or model "correction" of notation. Figure evidence must display the original crop or
artifact when authorized; generated captions remain non-authoritative, structural labels are not
image interpretation, and an abstention caused by unavailable visual interpretation must be
communicated clearly. Question-bank, question-paper and answer-key citations must retain assessment
classification and must not visually masquerade as guideline or reference material.

A conflict outcome must not render as a normal single-answer card: present a conflict-aware state
and, where safe and authorized, the conflicting excerpts that caused abstention, without letting the
UI choose a winner by retrieval rank, CrossEncoder score or source ordering. Insufficient evidence
must be stated concisely without filling the gap from pretrained knowledge or implying the system
probably knows the answer, allowing inspection of what was retrieved where appropriate. A
verification abstention must not display the rejected draft or raw verifier text. A provider failure
must be shown as a technical failure distinct from insufficient medical evidence, without exposing
secrets or raw error prose.

## Progress, streaming, inspector and enablement

The UI may show bounded non-sensitive stages such as searching sources, reranking evidence, checking
evidence sufficiency, generating a grounded draft and verifying claims, without internal scores.
**Do not stream unverified answer tokens while M8 verification has not completed.** If streaming is
desired, stream status and progress events and reveal the verified answer after verification; if
verified token streaming is impractical, return the final answer atomically. Safety takes priority
over perceived responsiveness.

Keep authorized developer and reviewer inspection available — M5 candidates, M6 reranked candidates,
EvidenceSet, M7 sufficiency decision and draft, M8 claims, verdicts, repair and final decision —
separated from the ordinary answer view and closed to unauthorized users.

M9 may finally make Ask functional, but not through one global boolean that bypasses safety. If the
contract includes `answering_enabled`, evolve it so the public Ask endpoint exists only under the
M9-safe pipeline, an answer is returnable only after M8 PASS, M7/M8 inspection routes keep exposing
their historical state correctly, and no earlier retrieval endpoint becomes an answer endpoint. Do
not retroactively change M5/M6/M7 response semantics, and document the enablement transition.

Do not modify ingestion state semantics to activate Ask. `RETRIEVAL_READY` means the corpus may
participate in retrieval, not that every question can be answered; answerability remains
request-specific through M7/M8, and no misleading global medical-readiness state may be created.

## Secrets, observability, performance and robustness

Provider secrets remain backend-only: never expose OpenAI, Anthropic or future provider keys or
Authorization headers to the frontend, and build no arbitrary provider-proxy endpoint. The browser
must not control prompts or provider endpoints. Preserve configuration-driven generation and
verification; do not hardcode a model identifier into the UI or orchestration, and obtain
provider/model identity from configured backend policy or trace.

Extend request tracing across the full path with bounded stages, preserving correlation ids and
recording result categories such as verified, insufficient, conflicting, abstained and
provider_failed, while keeping raw questions, source text and provider responses out of metric
labels. Record security- and operationally meaningful audit events where the existing architecture
applies, without excessive sensitive logging.

Measure end-to-end Ask latency, separating retrieval, reranking, evidence assembly, sufficiency,
generation, verification, source resolution and total. M8 already showed generation and verification
dominate; do not hide that, and claim no production SLO that has not been established.

Prevent obvious duplicate submissions, handle browser cancellation and navigation safely, and do not
let a client retry cause uncontrolled duplicate provider calls where idempotency is appropriate.
Ensure the experience works across reasonable desktop and mobile layouts — the inspector already hit
a 390 px overflow problem — and provide keyboard-accessible citation and source interactions where
practical.

## Testing and documentation

Extend the existing synthetic E2E corpus rather than replacing it, covering a verified factual
answer, a verified multiple-citation answer, insufficient evidence, conflicting evidence, an M8
abstention, provider failure, table and formula citations, figure-related abstention or source
display, question-bank evidence, cross-tenant rejection, citation clicks and page or bbox
navigation. Claim no clinical validation.

Backend tests must cover Ask orchestration, PASS-only answer delivery, absence of draft leakage,
insufficient, conflict, verification-abstention and provider-failure results, tenant isolation,
conversation ownership, citation and page/artifact authorization, and persistence if added, with an
explicit test that an M7 draft cannot escape when M8 fails. Frontend tests must cover verified answer
rendering, citations, the source panel, insufficient, conflict, abstention and provider-failure UI,
loading and progress, absence of unverified draft visibility, table/formula/figure handling and
responsive layout.

Run live browser scenarios, and because the local worker parses at `MAX_CONCURRENCY=1`, avoid running
heavy ingestion or regression workloads concurrently with latency-sensitive Playwright verification;
do not hide queue-contention flakiness and test against a drained queue for canonical results.

Using the configured backend OpenAI provider and a synthetic corpus, run at least one live question →
M5 → M6 → M7 → real generator → M8 real verifier → PASS → rendered verified answer → citation click →
source provenance, and also test one non-PASS branch without forcing generation. Never log or expose
the API key. One successful live call proves integration, not clinical quality; state that explicitly.

If persistent conversations are introduced, design tenant-scoped relational entities, create an
Alembic migration, test upgrade and downgrade, and enforce composite tenant ownership where the
architecture requires it. If no persistence is needed, create no empty migration, and document the
choice either way.

Create or update the M9 architecture documentation and an ADR if convention requires, covering Ask
orchestration, the public response contract, the verified-answer-only display rule, the conversation
model, citation and source navigation, the PDF/page/bbox viewer, the table/formula/figure viewers,
conflict and abstention UI, streaming policy, authorization and the M8→M9 boundary. Create
`docs/verification/m9.md` with the Git baseline, scope, Ask contracts, conversation persistence,
migration, authorization, UI states, citation and source viewers, table/formula/figure behaviour,
