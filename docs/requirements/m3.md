# 3. CRITICAL M2 COMPATIBILITY RULE

M2 discovered that Docling semantic classifications can differ between Windows host and Linux worker for borderline regions.

Therefore M3 must NOT make chunk boundaries depend exclusively on unstable semantic labels such as:

* caption vs paragraph
* header/footer edge cases
* formula vs text edge cases
* list grouping edge cases

Chunk construction should prioritize stable signals:

1. source document/version
2. page
3. reading order
4. normalized text
5. hierarchy where reliable
6. explicit artifact relationships
7. bounding boxes
8. deterministic structural rules

Semantic labels may assist chunking but must not become the only determinant of chunk identity.

Document this decision.

# 4. CHUNKING ARCHITECTURE

Implement hierarchical chunking:

```text
Document
  ↓
Logical structural region
  ↓
Parent chunk
  ↓
Child chunks
```

The retrieval system in later milestones should search primarily over smaller child chunks while retaining parent relationships for context expansion.

Conceptually:

```text
Chapter / Section
    ↓
Parent Chunk
    ├── Child 1
    ├── Child 2
    ├── Child 3
    └── Child 4
```

Do not use simple fixed-size character splitting as the primary algorithm.

# 8. TOKENIZER-AWARE CHUNKING

Use tokenizer-aware sizing.

Do not use:

* character counts
* word counts alone

as the final chunk-size mechanism.

Create a tokenizer abstraction.

The tokenizer used for chunk measurement must be versioned/configured.

Do not require OpenAI API access.

If using a Hugging Face tokenizer for MedCPT or another future embedding model, load it locally.

Chunking must work offline.

# 9. INITIAL CHUNK TARGETS

Start with configurable benchmark values approximately:

Child chunks:

`300–450 tokens`

Parent chunks:

`1000–1600 tokens`

These are starting parameters, NOT medical correctness constants.

Do not hard-code them in domain logic.

All values belong in typed configuration.

M3 evaluation should determine whether other sizes perform better.

---

# 10. SEMANTIC BOUNDARIES

Preferred split boundaries:

1. section/subsection
2. paragraph boundary
3. list boundary
4. sentence boundary
5. deterministic token split only as last resort

Never cut arbitrarily through:

* formulas
* table rows
* question/options
* captions
* clinically meaningful bullet lists

unless unavoidable.

---

# 11. PARENT CHUNKS

Parent chunks represent coherent larger context.

Examples:

* subsection
* small section
* group of consecutive paragraphs under one heading

Parent chunks should be suitable for later context expansion.

Do not generate parents so large that they routinely exceed useful generation context.

Parent chunks must preserve child ordering.

---

# 12. CHILD CHUNKS

Child chunks are retrieval units.

They should maximize:

* semantic focus
* context sufficiency
* exact terminology retention
* provenance
* retrieval precision

Avoid chunks containing multiple unrelated topics merely to hit a token target.

Chunk target size is a ceiling/goal, not a reason to combine unrelated sections.

---

# 13. OVERLAP POLICY

Do NOT default to arbitrary 20% text duplication.

Prefer structural overlap.

For example:

```text
Heading context
+
current paragraph group
+
minimal neighbouring context
```

Where conventional overlap is needed, make it configurable and benchmarked.

Repeated headings should preferably be represented as chunk metadata/context rather than duplicated excessively.

---

# 14. HEADING CONTEXT

Every child chunk should retain relevant structural ancestry.

For example:

```text
Book:
Harrison's Principles of Internal Medicine

Chapter:
Disorders of the Thyroid Gland

Section:
Hyperthyroidism

Subsection:
Treatment
```

Do not necessarily inject the entire hierarchy into `raw_text`.

Store hierarchy structurally.

Later, a retrieval representation may optionally prepend compact context.

Keep:

* source text
* retrieval representation

conceptually separable.

---

# 15. TABLE CHUNKING

Tables require specialized logic.

Never feed table contents into the generic text splitter.

## Small table

If within configured size:

`one table = one chunk`

Retain:

* caption
* headers
* cells
* page
* table ID
* surrounding section hierarchy

## Large table

Split by logical row groups.

Every table-part chunk must repeat enough header context to make the rows interpretable.

Example:

```text
TABLE:
Normal biochemical ranges

HEADERS:
Analyte | Lower | Upper | Unit

ROWS:
...
```

A table-part chunk must retain its relationship to the original complete table.

---

# 16. COMPLEX TABLES

Handle:

* multi-level headers
* merged cells
* row headers
* footnotes
* continuation pages

Do not flatten these destructively.

Retain canonical structured-table metadata.

Create a deterministic textual retrieval representation in addition to structured cells.

Example concept:

```text
Table: Drug dosing in renal impairment

Column headers:
Drug | eGFR category | Recommended dose

Row:
Metformin | 30–44 | ...
```

Do not use an LLM to summarize tables during M3.

---

# 17. MULTI-PAGE TABLES

M2 preserved continuation flags without destructive merging.

M3 should consume those relationships conservatively.

If continuation is confidently established:

* maintain shared table-group metadata
* allow chunks from each continuation part to reference the group

Do not merge uncertain continuation tables into fabricated single tables.

---

# 18. FORMULA CHUNKING

A formula should remain atomic.

A formula chunk should contain:

* exact formula
* formula source artifact ID
* heading context
* immediately associated definition/explanation where deterministically related
* page provenance

Example:

```text
Formula:
MAP = (SBP + 2 × DBP) / 3

Definitions:
MAP = mean arterial pressure
SBP = systolic blood pressure
DBP = diastolic blood pressure
```

Only include definitions actually present in source context.

Do not derive them from model knowledge.

---

# 19. FIGURE CHUNKS

M3 must NOT attempt visual interpretation.

Create figure-context chunks from source metadata:

* caption
* nearby deterministic explanatory text
* hierarchy
* page
* figure artifact ID

The original figure crop remains separate.

Example chunk metadata:

```text
chunk_type = FIGURE_CONTEXT
figure_id = ...
caption = ...
source_page = ...
```

Later a multimodal model may receive the original image.

Generated image descriptions must not be introduced in M3.

# 22. QUESTION + OPTIONS MUST STAY TOGETHER

Example:

```text
Question:
Which nerve supplies the diaphragm?

A. Vagus
B. Phrenic
C. Median
D. Radial
```

must not become:

```text
Chunk 1:
Question + A + B

Chunk 2:
C + D + Answer
```

Question boundaries override token targets within reasonable configured limits.

For oversized question explanations, keep:

* question chunk
* explanation child chunk(s)

with explicit relationship.

---

# 23. ANSWER KEYS

If source explicitly contains:

```text
Answer: B
```

store it as source content.

If source does not contain an answer:

`explicit_answer = NULL`

Never infer the answer.

Do not consult textbooks to “repair” question-bank answers during chunking.

That comparison belongs later in evidence/retrieval logic.

---

# 24. QUESTION AUTHORITY

Every question artifact/chunk must inherit source authority metadata.

Question-bank answer keys are not automatically authoritative medical truth.

Preserve:

* source type
* edition/year
* authority level

Later retrieval can distinguish:

```text
assessment content
```

from:

```text
medical reference evidence
```

---

# 25. LISTS

Medical content often has clinically significant lists:

```text
Contraindications:
- ...
- ...
- ...
```

Avoid splitting list header from list items where possible.

If list is too large:

* repeat list heading/context
* split by logical item groups

Retain list semantics.

---

# 26. DEFINITION / TERM STRUCTURES

Preserve term-definition pairs where detected structurally.

Example:

```text
Orthopnea:
Breathlessness occurring when lying flat.
```

Avoid separating definition from term.

Do not use LLM semantic extraction.

---

# 27. FOOTNOTES

Footnotes associated with:

* tables
* formulas
* paragraphs

should stay accessible to relevant chunks.

Do not discard medically meaningful qualifiers.

If footnote association is uncertain, preserve provenance without fabricating relationship.

---

# 28. PAGE HEADERS / FOOTERS

M2 identifies these where possible.

Default M3 policy:

* exclude repetitive PAGE_HEADER / PAGE_FOOTER from main retrieval chunks
* retain them in provenance/raw parse
* allow configuration override

Because M2 labels may vary across environments, do not rely solely on label.

Consider deterministic repetition signals if already available.

Do not aggressively delete text if classification is uncertain.

---

# 29. NORMALIZED RETRIEVAL TEXT

Each chunk may have two representations:

## Source representation

Faithful normalized source text.

## Retrieval representation

Deterministically enriched with context such as:

```text
Chapter: ...
Section: ...
Table: ...
```

Do not use an LLM to create summaries.

The original source representation must remain available.

# 30. CHUNK HASHING

Generate stable chunk hashes.

Hash should derive from relevant immutable data such as:

* source element identity/content
* chunk configuration version
* deterministic ordering

This will later support:

* idempotency
* incremental embedding
* change detection
* index reconciliation

Do not use random UUID alone for content identity.

# 31. IDEMPOTENCY

Duplicate worker delivery must not produce duplicate active chunks.

Same combination of:

* DocumentVersion
* ParseRun
* chunker version
* chunk config version

should resolve idempotently unless force-rechunk is explicitly requested.
