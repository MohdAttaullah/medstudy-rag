# M10 — ENTERPRISE CONFIGURATION UI + CONTROLLED POLICY MANAGEMENT

Continue development of the existing **Enterprise Medical RAG** repository.

M0–M9 are complete and independently verified.

M9 must already be committed as a clean Git checkpoint before beginning this milestone.

This task is:

**M10 — Enterprise Configuration UI + Controlled Runtime Policy Management**

Do NOT redesign M0–M9.

Do NOT begin M11 or M12.

M10 must make appropriate settings configurable **without allowing unsafe runtime mutation, index incompatibility, historical-policy loss, or frontend-controlled security decisions**.

```text
determinism

```

# 4. CLASSIFY EVERY SETTING

Every exposed setting must carry a lifecycle classification.

At minimum:

```text
RUNTIME_SAFE
RESTART_REQUIRED
REINDEX_REQUIRED
```

Where the real architecture requires finer distinctions, add explicit types such as:

```text
RECHUNK_REINDEX_REQUIRED
REPARSE_RECHUNK_REINDEX_REQUIRED
NEW_CORPUS_VERSION_REQUIRED
IMMUTABLE
SECRET_MANAGED_EXTERNALLY
```

Prefer accurate semantics over forcing everything into only three buckets.

---

# 5. EXAMPLES THAT MUST REMAIN TRUE

Examples from the architecture:

```text

→ runtime-safe

→ runtime-safe

embedding model
→ reindex-required

→ reindex-required
```

Changing embedding/index semantics must never silently reuse incompatible vectors.

---

# 6. DO NOT MIX INCOMPATIBLE INDEXES

Changing any setting that alters embedding/vector semantics must not mutate the current active index in place.

Examples:

```text
embedding model
embedding revision
pooling
vector dimension
normalization
distance metric
document representation
```

must result in a controlled new index/version workflow.

Never reinterpret old vectors under new semantics.

---

# 7. CHUNKING CONFIGURATION

Expose only settings actually supported by the deterministic M3 chunker.

Potential categories include:

```text
token budgets
parent/child sizing
table row-group behavior
question-bank atomicity policy
figure context limits
formula handling
```

But preserve M3 invariants.

Do not allow UI settings that make:

```text
question + options non-atomic
formula non-atomic
source provenance optional
silent truncation possible
```

Changing chunk semantics requires a new chunk run and downstream reindexing.

---

# 8. RETRIEVAL CONFIGURATION

Expose approved runtime-safe retrieval policy such as, where implemented:

```text

retrieval mode
```

Do not allow:

```text
direct addition of raw dense + BM25 scores

```

Validate ranges server-side.

---

# 9. MODEL CONFIGURATION

Potential model categories:

# 14. GROUNDING / SUFFICIENCY CONFIGURATION

# 20. CONFIGURATION SOURCE OF TRUTH


---

# 21. EFFECTIVE VS DESIRED CONFIGURATION

For non-runtime-safe settings, distinguish:

```text
CURRENT / EFFECTIVE
```

from:

```text
DESIRED / PENDING
```

Example:

```text
embedding model:
effective = MedCPT revision A
desired = revision B
status = REINDEX_REQUIRED
```

Do not show the new value as active before the corresponding controlled rebuild/activation actually succeeds.

---

# 22. CHANGE IMPACT

Before applying a setting change, return an impact description.

Examples:

```text
Applies immediately

Requires API restart

Requires retrieval service restart

Requires new embedding/index version

Requires reparse → rechunk → reindex

Requires new corpus activation
```

The backend computes impact.

Do not let the browser decide impact classification.

---

# 23. FAIL-CLOSED CHANGE APPLICATION

If an unsafe or incompatible setting change cannot be completed:

```text
retain current effective configuration
```

Do not partially activate a new policy.

This should follow the same staged/activation philosophy already used for indexes.

---

# 26. AUTHORIZATION

Configuration read/write must be server-authorized.

Ordinary `reader` users must not mutate system configuration.

Use the existing RBAC system.

Likely capabilities should distinguish:

```text
settings:read
settings:write
```

or equivalent.

Test 403 behavior explicitly.

---

# 27. TENANT VS GLOBAL SETTINGS

Do not casually make every setting tenant-specific.

Classify whether settings are:

```text
global/system
tenant
corpus
request-policy
```

Embedding model/index semantics may be tied to corpus/index versions.

Provider selection may be global or tenant-configurable depending on existing architecture.

Document the decision.

---

# 28. CONCURRENCY CONTROL

Prevent two admins from silently overwriting each other's changes.

Use an appropriate mechanism such as:

```text
revision/version
ETag
optimistic concurrency token
```

if persisted settings are mutable.

A stale update should fail clearly rather than overwrite newer configuration.

---

# 29. VALIDATION

Validate all settings server-side.

Examples:

```text

```

```text

unknown retrieval mode
```

# 30. CONFIGURATION PREVIEW

Where practical, allow a proposed change to be previewed before activation.

Return:

```text

```

without changing active state.

This is especially useful for destructive/rebuild-required settings.

---

# 31. REINDEX-REQUIRED CHANGES

M10 does not need to redesign the ingestion/indexing engine.

But for a setting that requires reindexing, the UI/API must not lie that it has become effective.

Either:

1. create a controlled pending configuration linked to the appropriate existing rebuild/version workflow, or
2. explicitly mark it pending and require the established operation outside M10.

Use whichever fits the repository architecture.

Do not invent a half-working rebuild system merely for UI completeness.

---

# 32. RESTART-REQUIRED CHANGES

For restart-required settings:

do not claim they are active until the relevant service has restarted with them.

If the project does not support orchestrating restart from the UI, clearly state:

```text

```

Do not add remote Docker/Kubernetes control casually.
