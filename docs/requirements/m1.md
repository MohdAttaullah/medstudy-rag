# MILESTONE OBJECTIVE

Implement **M1 only**:

> Authorized document upload, document metadata management, durable ingestion-job creation, state tracking, validation, persistence and operational visibility.

Do NOT implement:

* Docling parsing
* production OCR
* chunk generation
* embeddings
* Qdrant indexing
* retrieval
* reranking
* LLM answering

Those belong to later milestones.

Medical answering must remain disabled.

The output of M1 should be a robust ingestion control plane onto which M2+ processing stages can later be attached.

# 5. STATE MACHINE

Implement explicit state transition rules.

Full expected lifecycle may be represented as:

```text
UPLOADED
VALIDATING
QUEUED
PARSING
NORMALIZING
CHUNKING
ENRICHING
EMBEDDING
INDEXING
VERIFYING_INDEX
READY

FAILED
QUARANTINED
NEEDS_REVIEW
CANCELLED
```

However, M1 may only actively execute:

```text
UPLOADED
→ VALIDATING
→ QUEUED
```

The application must reject illegal transitions.

Do NOT let arbitrary application code write status strings directly.

Create a dedicated state-transition service/domain layer.

Examples that must fail:

```text
UPLOADED → READY
QUEUED → READY
FAILED → PARSING
CANCELLED → VALIDATING
```

unless future formally defined retry/recovery rules explicitly permit them.

Every successful transition must generate state history/audit information.

# 6. FILE UPLOAD SECURITY

Treat every file as untrusted.

At minimum validate:

* allowed MIME type
* filename
* extension
* maximum file size
* empty file
* content signature/magic bytes where practical
* PDF validity at a basic structural level
* duplicate checksum
* storage success

For M1, initial supported file type should preferably be:

```text
PDF
```

Do not add DOCX/PPTX/images simply for breadth unless architecture explicitly requires them now.

Better to make PDF ingestion reliable first.

Reject misleading extension/MIME combinations.

Sanitize filenames.

Never use the original filename directly as the storage path.

Generate internal object keys using UUIDs.

Prevent:

* path traversal
* executable upload
* unsafe filename use
* uncontrolled memory buffering for large uploads

Use streaming upload where appropriate.

Do not log raw uploaded document contents.

---

# 7. DUPLICATE HANDLING

SHA-256 must be computed.

Distinguish between:

### Exact duplicate upload

Same checksum already exists.

The API should return a deterministic duplicate indication rather than silently creating unnecessary copies.

### New edition/version

Different file/checksum but same logical publication.

Allow creation as a new `DocumentVersion`.

Do not try to use fuzzy document matching in M1.

Keep duplicate handling deterministic.

---

# 8. OBJECT STORAGE

Use the existing S3-compatible abstraction.

Local development:

```text
MinIO
```

Do not couple domain code directly to MinIO SDK specifics.

Create an object-storage abstraction such as:

```text
ObjectStorage
    put()
    exists()
    delete()
    stat()
    generate_read_reference()
```

or equivalent.

Implementation:

```text
S3ObjectStorage
```

Do not expose public buckets.

Persist only storage object keys/references in PostgreSQL.

Suggested storage convention:

```text
documents/
  <document-id>/
    <document-version-id>/
      original/
        source.pdf
```

Do not depend on human-readable filenames for object identity.

# 9. ATOMICITY / FAILURE HANDLING

Think carefully about:

```text
DB record created
but object upload fails
```

and:

```text
object uploaded
but DB transaction fails
```

Do not leave uncontrolled orphaned state.

Implement a clear compensating/transaction strategy.

Examples:

* upload to temporary object key
* validate
* persist metadata transaction
* promote/finalize object key

or another well-justified strategy.

Document the chosen approach.

Add failure-path tests.

# 10. AUTHORIZATION

M1 explicitly requires **authorized upload**.

Do not fake security by accepting a `user_id` from the request body.

If M0 already has an authentication abstraction, use it.

If full authentication was intentionally deferred, implement the minimum architecture needed to distinguish:

* authenticated caller
* role/permission
* unauthorized request

without prematurely building an entire enterprise identity system.

At minimum define permissions such as:

```text
document:read
document:upload
document:manage
ingestion:read
ingestion:retry
ingestion:cancel
```

Server-side authorization is mandatory.

Frontend buttons are not authorization controls.

Write tests proving unauthorized callers cannot upload/manage documents.

If M0's architecture intentionally defers authentication implementation to a later milestone, implement a clearly marked local/dev principal adapter behind an auth interface while preserving server-side authorization boundaries.

Do NOT pretend that this constitutes production authentication.

Document the limitation.

# 12. CELERY / QUEUE BOUNDARY

M1 needs durable queue integration but does not implement actual parsing.

After validation succeeds:

```text
VALIDATING
→ QUEUED
```

enqueue a placeholder/future-compatible ingestion task.

The Celery task boundary must be real and testable.

However:

the task should NOT pretend to parse documents yet.

It may safely confirm receipt or remain as the M2 processing entry point according to architecture.

The persisted DB state remains the source of operational truth.

Do not use Redis alone as the job state store.

# 13. IDEMPOTENCY

The upload workflow and job creation must handle retries safely.

Support an idempotency strategy for upload initiation/job creation where appropriate.

Consider:

```text
Idempotency-Key
```

for API requests.

A network retry must not accidentally create:

```text
DocumentVersion A
DocumentVersion B
DocumentVersion C
```

for the same request.

Document the semantics.

Test them.

# 24. PERFORMANCE

Uploads may later involve large books.

Do not load the entire file into memory unnecessarily.

Use bounded/streaming processing.

Object-storage upload should support large files.

M1 does not need premature distributed optimization, but the implementation must not fundamentally assume tiny PDFs.
