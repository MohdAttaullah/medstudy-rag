# 2. M2 OBJECTIVE

Implement:

> Reliable conversion of an uploaded immutable PDF into a validated, structured, provenance-preserving internal document representation using Docling.

M2 must transform:

```text
Original PDF
    ↓
Docling parser
    ↓
Raw structured artifact
    ↓
Normalized internal document model
    ↓
Page + element provenance
    ↓
Parsing-quality validation
    ↓
PARSED / NORMALIZED result ready for M3
```

M2 is NOT responsible for retrieval.

M2 must NOT implement:

* production chunking
* embeddings
* Qdrant indexing
* BM25 retrieval
* RRF
* reranking
* LLM answering
* claim verification
* medical chat

Those remain later milestones.

# 3. M2 STATE FLOW

Extend the currently real ingestion execution path from:

```text
QUEUED
```

to:

```text
QUEUED
   ↓
PARSING
   ↓
NORMALIZING
   ↓
ENRICHING
   ↓
READY_FOR_CHUNKING
```

If the existing state model already contains a later generic state such as `CHUNKING`, do NOT enter it yet.

If necessary, introduce a semantically precise intermediate state such as:

`PARSED`

or:

`READY_FOR_CHUNKING`

only if doing so is consistent with the existing state-machine design and ADRs.

Do not fake M3 completion.

M2 must stop before actual production chunk generation.

Failure outcomes should include:

```text
FAILED
QUARANTINED
NEEDS_REVIEW
CANCELLED
```

according to reason.

# 4. DOCLING AS PRIMARY PARSER

Use Docling as the primary PDF document-understanding system.

Do not simply extract PDF text with PyPDF and call that parsing.

Preserve Docling structure.

The parser should recognize as available:

* title
* headings
* paragraphs
* lists
* tables
* formulas
* figures/pictures
* captions
* page boundaries
* reading order
* bounding boxes
* document hierarchy

Use Docling's structured document representation wherever practical.

Do not flatten the document prematurely.

---

# 5. PARSER ABSTRACTION

Do not couple the entire ingestion domain directly to Docling.

Create a parser interface approximately like:

```python
class DocumentParser(Protocol):
    def parse(self, source: ParseSource, config: ParserConfig) -> ParsedDocument:
        ...
```

Implementation:

```text
DoclingDocumentParser
```

This allows future alternate parsers without rewriting ingestion orchestration.

Docling-specific structures must be translated through a controlled normalization boundary.

---

# 6. PARSER VERSIONING

Every parse operation must record enough information to reproduce/understand its output.

Record:

* parser provider
* parser name
* Docling version
* parser configuration version
* OCR configuration
* table extraction configuration
* processing timestamp
* source DocumentVersion
* source checksum

Do not treat parsing as an unversioned black box.

If the parser/configuration changes materially later, the system should support reparsing into a new parse artifact/version rather than silently overwriting history.

---

# 7. RAW PARSE ARTIFACT

Store the raw structured Docling output as an immutable processing artifact.

Suggested object-storage path:

```text
documents/
  <document-id>/
    <document-version-id>/
      original/
        source.pdf
      parsing/
        <parse-run-id>/
          docling.json
```

Potentially also retain:

```text
parse-metadata.json
```

Do not rely only on PostgreSQL to store the full parser output.

The raw parse artifact is useful for:

* debugging
* future re-normalization
* parser comparison
* reproducibility

Store artifact metadata in PostgreSQL.

# 9. HIERARCHY

Preserve document hierarchy where parser evidence supports it.

Example:

```text
Book
 └── Chapter
      └── Section
           ├── Paragraph
           ├── Paragraph
           ├── Table
           ├── Figure
           └── Formula
```

Represent relationships explicitly.

Possible mechanisms:

* parent_element_id
* hierarchy level
* logical path
* section ancestry

Do not invent chapter/section hierarchy where the parser does not support it.

It is acceptable to represent unknown structure honestly.

# 10. READING ORDER

Reading order is critical for:

* two-column books
* boxed notes
* sidebars
* figure captions
* tables

Store a deterministic reading order.

Do not assume raw PDF object order equals human reading order.

Add tests covering multi-column layouts where practical.

# 11. BOUNDING BOX PROVENANCE

Every element that Docling can localize should retain page-region provenance.

Store a normalized bounding-box representation.

For example:

```text

y1
x2
y2
coordinate_space
```

or another well-defined schema.

Document:

* origin convention
* coordinate units
* page rotation handling
* whether values are absolute or normalized

Do not store ambiguous coordinates.

Later, the user must be able to click a citation and highlight the exact source region.

M2 is where this becomes possible.

# 13. TABLE NORMALIZATION

Create a deterministic normalized table representation.

Example internal shape:

```json
{
  "headers": ["Analyte", "Lower", "Upper", "Unit"],
  "rows": [
    ["Sodium", "135", "145", "mmol/L"],
    ["Potassium", "3.5", "5.0", "mmol/L"]
  ]
}
```

But do not lose richer cell structure where the source includes:

* merged cells
* multi-level headings
* row headers
* notes

If the simple representation is insufficient, retain both:

1. canonical structured table
2. convenient text/Markdown rendering

The canonical structure remains primary.

# 17. OCR

Handle scanned PDFs deliberately.

Detect when pages contain insufficient native text and OCR is required.

Use the OCR capabilities supported by the chosen Docling pipeline/configuration.

Record:

```text
ocr_used
ocr_engine
ocr_config
```

per parse run and ideally per page where possible.

Do not silently OCR everything at maximum cost.

Do not use an LLM as OCR.

---

# 18. OCR QUALITY

OCR output is not automatically trustworthy.

Store quality signals where available.

Flag suspicious pages such as:

```text
very low extracted character count
high OCR uncertainty
abnormally many invalid characters
no meaningful text despite visually non-empty page
```

Such conditions can lead to:

`NEEDS_REVIEW`

rather than allowing corrupted content to proceed invisibly.

---

# 19. HEADER / FOOTER HANDLING

Medical books frequently repeat:

```text
chapter name
book title
page number
copyright
```

on every page.

Identify repetitive page headers/footers when confidently possible.

Do not delete them irreversibly from the raw parsed artifact.

Instead mark them semantically:

```text
PAGE_HEADER
PAGE_FOOTER
```

The M3 chunker can then exclude or downweight them.

---

# 20. FOOTNOTES

Preserve footnotes separately where possible.

Footnotes can materially change:

* drug dosing
* contraindications
* table interpretation
* formula meaning

Do not simply discard small-font text.

Retain association with:

* page
* table
* paragraph

where parser evidence supports it.

# 21. CAPTION ASSOCIATION

Examples:



# 22. MULTI-PAGE TABLES

Medical books often have tables spanning several pages.

Do not automatically assume page break means new table.

Where Docling or deterministic heuristics identify continuation:

represent table continuation relationships.

For example:

```text
table_group_id
continuation_of
```

Do not merge uncertain tables destructively.

If uncertain, preserve them separately with a possible-continuation relationship/flag.

---

# 23. QUESTION-BANK RECOGNITION

M2 should prepare for question banks but should NOT yet perform final production question chunking.

Recognize candidate patterns where deterministic parsing makes this possible:

* numbered questions
* A/B/C/D options
* answer labels
* explanation headings

But treat these as structural hints.

Do not use an LLM to infer missing answers.

Do not mark a guessed answer as official.

The final Question/Options/Answer logical-object extraction belongs primarily to M3 unless architecture already places deterministic normalization in M2.

If implementing candidate structures now, clearly distinguish:

```text
EXPLICIT_SOURCE_CONTENT
```

from:

```text
INFERRED_STRUCTURE
```

---

# 24. NO MEDICAL CONTENT CORRECTION

Very important:

M2 must NOT "fix" extracted medical facts.

For example, if the PDF says:

```text
Na 135–145 mmol/L
```

store what the source says.

Do not have an AI decide that a value "looks wrong" and rewrite it.

Parsing correctness is about fidelity to the document, not medical truth correction.

---

# 25. NORMALIZATION

Normalization may safely include deterministic operations such as:

* Unicode normalization
* whitespace cleanup
* line-break repair
* soft-hyphen handling
* ligature normalization
* stable newline policy

But retain the original extracted content or raw parse artifact.

Never make normalization irreversible.

Where text changes materially, retain both:

```text
raw_text
normalized_text
```

# 26. PARSING QUALITY VALIDATION

Build a quality-validation layer.

Do not declare every successful Docling execution a successful ingestion.

Create measurable checks.

Examples:

### Document-level

* expected page count vs parsed page count
* non-empty page ratio
* element count
* text character count
* table count
* figure count
* formula count
* duplicate element anomalies
* invalid bbox count
* missing page associations

### Page-level

* empty page with visually non-empty source
* extremely low text density
* OCR failure
* malformed reading order
* overlapping impossible coordinates
* invalid dimensions

### Artifact-level

* table has zero rows
* table cell coordinates malformed
* figure crop missing
* formula content empty
* caption reference unresolved

# 28. FAIL-CLOSED RULES

Examples:

### FAIL / FAILED

* source PDF cannot be opened
* parser crashes irrecoverably
* raw parse artifact cannot be persisted
* page count reconciliation catastrophically fails
* normalized data violates required integrity

### NEEDS_REVIEW

* substantial pages lack extractable content
* OCR quality is suspicious
* many tables appear malformed
* severe layout ambiguity

### PASS_WITH_WARNINGS

* isolated low-confidence page
* optional preview failure
* one unresolved caption relationship

Keep thresholds configurable.

---

# 29. IDEMPOTENCY

Parsing must be safely retryable.

If the same:

```text
document_version
+
parser version
+
parser config version
```

has already completed successfully, do not accidentally create duplicate normalized data unless a forced reparse is explicitly requested.

Design parse-run identity/version semantics clearly.

---

# 30. REPROCESSING

Support future reparse workflows.

Do not overwrite the prior successful parse in place.

Example:

```text
DocumentVersion
   ├── ParseRun v1
   └── ParseRun v2
```

Only one parse run may be designated active/current for downstream processing.

Changing active parse must be controlled.

---

# 31. TRANSACTIONAL BEHAVIOR

Parsing writes many objects.

Do not leave a partially normalized document marked successful.

Use clear lifecycle:

```text
ParseRun = PROCESSING
     ↓
create pages/elements/artifacts
     ↓
validation
     ↓
ParseRun = COMPLETED
```

Failure should leave enough state for diagnostics/retry while ensuring incomplete parse output is not consumed by downstream processing.

# 54. M2 DEFINITION OF DONE

M2 is complete only when:

* queued PDFs are actually parsed by Docling
* raw Docling artifact is persisted
* ParseRun is durable
* pages are persisted
* structured elements are persisted
* hierarchy is retained where available
* reading order is retained
* bbox provenance is retained
* tables retain structure
* formulas are explicit artifacts/elements
* figures retain original crops/provenance
* captions retain relationships
* OCR path is supported/configured
* parser/config version is recorded
* normalization is deterministic
* parse-quality validation exists
* suspicious parses can become NEEDS_REVIEW
* catastrophic parses fail closed
