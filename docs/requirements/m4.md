# M4 — BIOMEDICAL EMBEDDINGS, QDRANT INDEXING, VERSIONING AND INDEX VALIDATION

The milestone request as received. Preserved verbatim in substance for cross-agent continuity, in
the same way as [M1](m1.md), [M2](m2.md), [M3](m3.md) and the original [bootstrap](bootstrap.md)
request. What was actually built and verified is recorded in
[the M4 report](../verification/m4.md); where the two differ, the report is the truth.

---

Continue development of the existing Enterprise Medical RAG repository. M0–M3 are complete and
verified. Expected starting point: M2 checkpoint `0d2085a`, M3 committed as a clean verified
checkpoint, uploaded PDFs parsed, normalized pages/elements/tables/formulas/figures present,
validated ChunkRuns present, deterministic retrieval-ready chunks present, jobs stopping at
`READY_FOR_EMBEDDING`, no vector embeddings or retrieval, Qdrant infrastructure present but with no
production corpus index, medical answering disabled.

**Objective.** Generate versioned biomedical dense embeddings from retrieval-eligible M3 chunks,
persist embedding and index metadata, load verified points into Qdrant, and make a validated index
available for M5 retrieval. M4 must NOT implement actual user-query retrieval.

## Required constraints

1. **Startup.** Read `AGENTS.md`, `CLAUDE.md`, `AI_HANDOFF.md`, the M3 verification report, the
   chunking, data-model and ingestion architecture and the relevant ADRs. Use the project skills.
   Inspect git state, the ChunkRun/Chunk models, the worker architecture, the Qdrant service and
   version, the configuration system and the state-machine guards. Run focused M3 verification
   before materially changing the indexing boundary. Do not recreate previous milestones.
2. **State flow.** Extend `READY_FOR_EMBEDDING` to approximately `EMBEDDING → INDEXING →
   VERIFYING_INDEX → READY_FOR_RETRIEVAL`, using names consistent with the existing architecture.
   Do not enable Ask. Do not implement query retrieval. `READY_FOR_RETRIEVAL` means only that
   embeddings are complete, expected points exist, index integrity checks passed and this
   corpus/index version is technically eligible for M5 — never that it is medically answerable.
3. **Model.** `ncbi/MedCPT-Article-Encoder` as the default dense document embedding model, behind
   an `EmbeddingModel` abstraction with a `MedCPTArticleEmbedder` implementation. Do not spread
   Hugging Face or PyTorch details through domain services.
4. **Pinning.** No floating `main`. Persist provider, model id, exact revision, tokenizer revision,
   model checksums where practical, transformers/tokenizers/torch versions, dimension, pooling,
   maximum input tokens, normalization policy, dtype, device class and configuration fingerprint.
   Validate expected artifacts at load. A model change must create a new `EmbeddingVersion`.
5. **Representation.** Follow the released MedCPT article semantics: Article Encoder, `[CLS]` last
   hidden state, 512 maximum input length, 768 dimensions. Do not substitute mean pooling unless
   benchmarked and versioned. Do not L2-normalize unless the architecture explicitly introduces and
   evaluates that change. Initial similarity metric `DOT`, because MedCPT retrieval is maximum
   inner product. Record the decision in an ADR.
6. **Input builder.** A deterministic `EmbeddingInputBuilder` derived entirely from the M3
   retrieval representation, with a two-field context/body representation. No invented summaries,
   no LLM. Persist or hash the exact embedding input.
7. **Source separation.** Maintain original source → parsed element → chunk source text → retrieval
   representation → embedding input → vector. Every vector must trace backward. Do not overwrite
   source text with embedding-specific formatting.
8. **Truncation.** Default policy `REJECT`. Never silently embed only the first portion: create a
   validation finding, mark the run for review or failure per policy, expose the offending chunk id
   and advise rechunking. Any future experimental truncation must never be silent. Test this.
9. **Eligibility.** An explicit policy. Initially `TEXT_CHILD`, `TABLE`, `TABLE_PART`, `FORMULA`,
   `FIGURE_CONTEXT`, `QUESTION`, `QUESTION_EXPLANATION`, `LIST` and `OTHER_STRUCTURED` where
   appropriate. Do not index `TEXT_PARENT` as a normal first-stage unit; parents are for later
   context expansion. Any experimental parent embeddings need a separate vector space or explicit
   retrieval-role metadata and must stay disabled by default.
10. **Question banks.** May be indexed, but the payload must preserve `source_type`,
    `authority_level`, question status and explicit-answer status so M5 can filter or weight them.
    Do not promote answer keys to textbook authority merely because they are embedded.
11–14. **Durable records.** `EmbeddingVersion` (vector semantics, not one run), `EmbeddingRun` (one
    ingestion attempt, with counts, fingerprints and safe errors), `ChunkEmbedding` (per-vector
    metadata with point id, input hash, vector checksum, dimension, token count and truncation
    flag; the dense array belongs in Qdrant). Vector checksums are for duplicate-delivery
    verification, corruption detection, environment comparison and reconciliation — never a
    semantic quality score.
15. **Numerical determinism.** Same revision, tokenizer, input and inference settings in a
    compatible environment should be sufficiently stable, but do **not** promise exact cross-device
    IEEE bit identity. Evaluate same-host repeated equality and host-versus-worker deviation, and
    record max absolute delta, similarity agreement and checksum behaviour. Do not hide hardware
    variance.
16. **CPU-first.** Must work without CUDA. Configurable batch size, bounded worker concurrency,
    configurable torch threads and dtype where safe.
17. **Offline model mode.** A predictable model-cache strategy; once provisioned the worker must
    run without repeatedly reaching Hugging Face. Document the cache location, provisioning
    workflow, revision pinning and offline behaviour. Do not rely on runtime downloads.
18–19. **Index abstraction.** A `VectorIndex` protocol with a `QdrantVectorIndex` implementation.
    Services must not depend directly on qdrant-client. Use **named vectors** so M5/M6 can add
    dense, sparse and late-interaction representations without changing point identity; M4 populates
    only `medcpt_dense`.
20. **Point identity.** One point per retrieval-eligible chunk, deterministic, derived from stable
    application identity. Never Qdrant-generated integer ids. Maintain a one-to-one
    Chunk ↔ ChunkEmbedding ↔ point reconciliation.
21. **Payload.** Routing, filtering and provenance metadata only. Do not duplicate complete source
    bodies into the payload; PostgreSQL remains the canonical content store and M5 resolves chunk
    ids there.
22–23. **Tenancy and indexes.** A shared collection with explicit tenant partitioning and a
    tenant-oriented indexed payload key, not one collection per user. Every retrieval operation must
    be tenant-scoped server-side; prove cross-tenant isolation at the repository/service boundary,
    never in the frontend. Create payload indexes before significant load, only for fields expected
    to be filtered, and document why each exists.
24–27. **Index versioning and activation.** A durable `IndexRun`/`IndexVersion` concept. Never
    expose partially indexed points as verified data: stage, upload, reconcile counts, payloads,
    vector names and dimensions, verify, then activate. Design activation explicitly; prefer
    collection aliases for atomic model/schema replacement; keep a durable PostgreSQL active-index
    pointer. Do not assume multiple Qdrant mutations form a transaction, and do not claim stronger
    atomicity than Qdrant provides. Building a replacement must not require deleting the old one.
28–31. **Pipeline.** `READY_FOR_EMBEDDING → EMBEDDING → load active ChunkRun → select eligible
    chunks → build deterministic input → token-limit validation → batched inference → persist
    metadata → INDEXING → batched upsert → VERIFYING_INDEX → reconcile → READY_FOR_RETRIEVAL`.
    Batch both inference and upserts. Tolerate worker interruption: skip verified embeddings,
    recompute mismatches, retry failed batches, resume uploads and reconcile at the end. Duplicate
    delivery must not create multiple active runs. Reuse a vector only on an exact input-hash,
    tenant and semantic-configuration match — never because text merely looks similar.
32–34. **Reconciliation and validation.** Verify expected and actual point counts, that all expected
    point ids exist, that no unexpected active points belong to the run, the vector name and
    dimension, required payload, tenant ids, chunk-id resolution, embedding-run ids, that no failed
    or truncated embeddings were promoted, and that the PostgreSQL ↔ Qdrant mapping is complete.
    Persist `IndexValidationFinding` rows with INFO/WARNING/ERROR/CRITICAL severities. Reject NaN,
    infinities, wrong dimensions, all-zero vectors and malformed tensors. Do not call any of this
    "semantic accuracy", and do not set arbitrary medical thresholds on embedding values.
35–37. **Evaluation.** M4 evaluation is not retrieval evaluation. Test dimension, deterministic
    input formatting, stable repeated inference, non-finite detection, max-token handling, batch
    versus single equivalence within tolerance, expected model revision, pooling, similarity
    configuration, point mapping and host/container comparison. Recall@K begins in M5. A very small
    non-authoritative semantic sanity check is acceptable but must not be called retrieval accuracy
    and must not be tuned against. Fixtures must be synthetic or public domain; no copyrighted
    medical corpora.
38–40. **Database, errors and failure recovery.** Protect one appropriate active EmbeddingRun per
    ChunkRun/config, one ChunkEmbedding per chunk/run/vector, valid dimensions, no active failed
    run, tenant/source lineage on IndexRun, activation only of VERIFIED runs and unique point
    mappings — with database constraints, not application assumptions alone. Declare error
    retryability and do not retry deterministic schema or model incompatibilities forever. Test
    Qdrant unavailable, unavailable mid-batch, partial upload, timeout after acceptance, duplicate
    batch, payload mismatch, schema mismatch and count mismatch. Do not delete the prior active
    index when a replacement fails.
41. **Security.** Qdrant is internal infrastructure: no public port assumption, no direct frontend
    access, no provider secrets in payloads, server-side tenant scope, and parsed/chunk text stays
    behind document authorization.
42–45. **APIs and UI.** Authorized inspection of embedding versions, embedding run detail, chunk
    embedding metadata, index run detail, index validation findings and index statistics. Do not
    expose raw 768-number vectors to ordinary users. Extend Document Details with real embedding and
    index state; add an Index Inspector with navigation from point metadata to chunk to source page;
    add the real stages to Operations. Do not show retrieval relevance scores — they do not exist.
46–47. **Observability.** Instrument embedding and Qdrant counters, avoiding high-cardinality labels
    such as chunk id. Record a performance baseline: chunk count, average input tokens, total
    embedding time, embeddings per second, indexing time, upsert throughput, and worker memory and
    collection size where practical. No arbitrary SLA claims.
48–49. **Migrations and tests.** Alembic migrations for the embedding and index tables and the
    state-machine extension, verified M3 → M4 → downgrade → upgrade → `alembic check` with no drift.
    Comprehensive unit, integration, failure, frontend and browser tests, including the real
    end-to-end path through the worker, the model, Qdrant, reconciliation and `READY_FOR_RETRIEVAL`.
50–51. **Environments.** The canonical embedding execution environment is the Linux worker. Compare
    host and worker inference on a fixed synthetic dataset and report whether vector bytes match,
    the numerical differences if not, ranking agreement and the model/tokenizer revisions. Do not
    fake bit-level determinism. Provision the model cache into a named volume with correct
    ownership, test clean-volume provisioning and document pre-provisioning.
52. **No provider keys.** M4 uses no OpenAI or Anthropic key and must not add one to runtime
    requirements. This stage is entirely local embedding and index infrastructure.
53–55. **Documentation and done.** Create or update `docs/architecture/embeddings.md`,
    `docs/architecture/vector-index.md`, the data model, ingestion architecture and
    `docs/evals/embedding-evaluation.md`, add an ADR covering the MedCPT choice, CLS pooling, 768
    dimensions, DOT similarity, named vectors, index versioning/activation and tenant partitioning,
    and write `docs/verification/m4.md` covering baseline git state, model id/revision, checksums,
    pooling, dimensionality, distance metric, embedding-input representation, truncation policy,
    eligible chunk types, Qdrant schema, tenant strategy, IndexRun activation semantics, migrations,
    API/UI, exact tests and results, performance baseline, host/container numerical comparison,
    known limitations, git state and confirmation that M5 was not started.
56. **Stop condition.** Stop after M4. Do not implement the MedCPT Query Encoder query path, BM25,
    sparse retrieval, RRF, query expansion, reranking, ColBERT, OpenAI, Claude or medical answering.
    The next milestone is **M5 — biomedical hybrid retrieval: MedCPT Query Encoder + dense search +
    BM25/sparse retrieval + reciprocal-rank fusion + retrieval-quality evaluation**, and it must not
    be started without explicit authorization.

**Priority.** VECTOR CORRECTNESS > INDEX CONSISTENCY > PROVENANCE > REPRODUCIBILITY > RESUMABILITY
> PERFORMANCE.
