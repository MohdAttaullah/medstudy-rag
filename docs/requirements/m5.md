# M5 — BIOMEDICAL HYBRID RETRIEVAL, QUERY ENCODING, BM25, RRF, AND RETRIEVAL QUALITY EVALUATION

The milestone request as received. Preserved in substance for cross-agent continuity, in the same
way as [M1](m1.md), [M2](m2.md), [M3](m3.md), [M4](m4.md) and the original [bootstrap](bootstrap.md)
request. What was actually built and verified is recorded in
[the M5 report](../verification/m5.md); where the two differ, the report is the truth.

---

Continue development of the existing Enterprise Medical RAG repository. M0–M4 are complete and
verified. Expected starting point: M4 committed as the verified checkpoint `d50521b`, uploaded PDFs
parsing, deterministic medical chunks present, MedCPT Article Encoder embeddings present, Qdrant
holding verified `medcpt_dense` vectors, active IndexRuns reconciled point for point, jobs stopping
at `READY_FOR_RETRIEVAL`, `searchable` still false, Ask disabled and no medical answering.

**Objective.** Build a tenant-safe, version-aware, accuracy-measured hybrid biomedical retrieval
pipeline using the MedCPT Query Encoder for dense retrieval, BM25 for lexical retrieval, Reciprocal
Rank Fusion for candidate fusion, and a gold retrieval dataset for Recall@K, MRR and nDCG
measurement. **M5 is retrieval only. Do not add answer generation.**

## Boundary

M5 begins at `READY_FOR_RETRIEVAL` and finishes at a precisely named state such as
`RETRIEVAL_READY`. Distinguish carefully between indexing complete, retrieval configuration
verified, and corpus medically answerable. M5 must not make the corpus answerable, must not make
`READY` reachable, and must not enable Ask.

## Pipeline

User query → MedCPT Query Encoder and BM25 in parallel → dense top-K and sparse top-K → RRF →
fused candidates → provenance hydration → retrieval result. **No reranker in M5**; M6 adds the
cross-encoder.

## Query side

Use `ncbi/MedCPT-Query-Encoder` behind a provider-independent `QueryEncoder` protocol; it is
deliberately a different model from the Article Encoder used for chunks, and the Article Encoder
must never be used for user questions. Pin model id, exact revision, tokenizer revision, model and
tokenizer checksums, torch/transformers/tokenizers versions, pooling, dimension, normalization
policy, maximum query length, dtype and a policy fingerprint. Provision offline as in M4; do not
depend on runtime network access. Follow the released query-side representation exactly; do not
mean-pool, normalize or change DOT/COSINE semantics silently. Query vectors must be compatible with
the stored Article Encoder vectors.

Measure query length with the model's own tokenizer. Never silently truncate: a question exceeding
the supported length returns a structured error. Implement deterministic normalization only —
Unicode, whitespace, harmless punctuation, preserving clinically meaningful symbols. **No LLM query
rewriter, no HyDE, no alternate queries, no paraphrase.** The original user query must remain
available. Do not introduce uncontrolled synonym or abbreviation expansion; establish a clean
baseline without expansion first.

## Dense lane

Search `medcpt_dense` using only the active PostgreSQL-resolved verified IndexRun; do not retrieve
based on the Qdrant alias. The authoritative path is tenant → active verified IndexRun →
collection → Qdrant. Every search must filter by tenant server-side. Make `retrieval.dense.top_k`
configurable; benchmark candidate values rather than assuming one.

## Lexical lane

Implement a real BM25 lane for exact medical terminology — `HLA-B27`, `CYP3A4`, `BRCA1`, `IL-6`,
`HbA1c`, `HER2`, `Na+/K+-ATPase`, drug names, rare disease names, abbreviations. Dense retrieval
alone is not sufficient. Build over the same retrieval-eligible M3 chunk set used by dense indexing;
do not index `TEXT_PARENT` by default; preserve tenant, chunk id, document, source type, authority
level and pages.

Create an explicit, versioned analyzer policy that does not destroy hyphenated gene names, `+`/`-`,
slash expressions, decimals, units or abbreviations. Implement behind a `SparseRetriever`
abstraction. Prefer an architecture where `medcpt_dense`, a sparse representation and a future
late-interaction representation can share one logical point identity; do not create a disconnected
document-id scheme for BM25 — chunk identity must remain shared across lanes.

Version the sparse index against the active ChunkRun, corpus version, analyzer version and BM25
parameters. Version `k1`, `b`, analyzer/tokenizer version, stopword policy and case policy; the
defaults are evaluation starting points, not optimal values. Start with stopwords disabled. Do not
assume lowercase-only indexing suffices; evaluate exact-term retrieval explicitly.

## Fusion

Fuse with Reciprocal Rank Fusion, `score(d) = Σ 1/(k + rank_i(d))`, behind a `RankFusion`
abstraction. Make the constant configurable; `k = 60` is a candidate, not a proven optimum.
**Do not fuse raw scores** — a MedCPT dot score and a BM25 score are not comparable distributions,
which is exactly why rank-based fusion is appropriate. Weights may exist in the architecture, but
the initial default should remain simple RRF unless evaluation proves otherwise. Do not tune
excessively against a tiny synthetic dataset.

## Results, provenance and policy

Create a common retrieval result model carrying chunk, document, version, chunk type, pages, each
lane's rank and score, the fused rank and score, authority level and source type. Scores and ranks
are retrieval diagnostics and must not be presented as medical confidence.

Hydrate canonical chunk content from PostgreSQL after candidate ids are retrieved; do not trust
client-provided chunk ids; maintain tenant scoping. Every result must still resolve back through
chunk → source elements → page → document version → document → original PDF. Return authority
metadata but do not use authority as the primary relevance score yet. Question chunks remain
searchable, but a question-bank match must not automatically outrank a textbook passage; measure
this rather than applying an arbitrary penalty.

Support structured filters where existing metadata allows. The tenant filter is mandatory and
cannot be disabled. Never query a failed, staging or unverified run, or an inactive superseded
ChunkRun, and test that stale index data cannot be returned.

Declare errors for query-encoder unavailability and revision mismatch, over-long queries, dense
index not ready, dense search failure, sparse index not ready, sparse version mismatch and sparse
search failure. Do not silently fall back to another model. Whether hybrid retrieval may degrade to
dense-only must be explicit policy; for accuracy-first mode the default should be **fail closed**.

Support explicit `DENSE_ONLY`, `BM25_ONLY` and `HYBRID_RRF` modes for comparison. Trace correlation
id, config version, encoder version, sparse index version, active IndexRun, query hash, top-k
values, fusion strategy, candidate count and latency; do not persist raw user queries in general
logs. Provide an authorized developer debug view showing the three rankings with rank, score, chunk
type, source, page, authority, preview and provenance link — not exposed unrestricted.

**No answer generation.** The retrieval UI must say "retrieved evidence candidates", never
"answer". Do not summarize results with an LLM.

## Evaluation

Create a gold retrieval dataset with graded or multi-relevant judgments, covering factual, exact
drug name, gene/biomarker, abbreviation, synonym-like, table, formula, figure, long question, short
keyword, question bank, answer key, cross-page, competing topics, negative, rare terminology,
numeric/unit-sensitive, multiple relevant, authority conflict and lexically-weak-semantically-strong
cases. Prefer synthetic or public-domain content first.

Include questions whose answer is absent, and capture top scores, candidate ranks and false
positives for a later evidence gate. Measure Recall@1/3/5/10/20, MRR and nDCG where graded
judgments exist; do not manufacture graded labels. Also measure Precision@K, but do not optimize
first-stage retrieval for precision alone. Report per category, produce a lane comparison table
populated only with actually measured values, and produce failure diagnostics with a probable
failure class. Do not automatically change architecture for an isolated failure.

If a retrieval failure clearly comes from chunk boundaries, do not silently change M3 semantics
within M5: document it, add a regression fixture, and evaluate old versus new separately. If MedCPT
underperforms in some category, record the evidence rather than replacing it impulsively. **Do not
implement ColBERT in M5.**

Measure query encoder, dense, BM25, fusion, hydration and end-to-end latency, and warm versus cold
behaviour; no arbitrary production SLA. Reuse one loaded encoder per evaluation run. Provision the
query encoder offline and fail closed if the pinned model is unavailable. Decide carefully where
interactive query encoding runs; a dedicated retrieval process is preferable to loading another
large transformer into every FastAPI worker, and the Article Encoder is not needed for interactive
search.

`scripts/evaluate_retrieval.py` must load the gold dataset, run all three lanes, compute metrics,
produce a JSON report and optional Markdown summary and failure diagnostics, and never call an LLM.
Reports must capture git commit, corpus/index identity, ChunkRun, EmbeddingVersion, Query Encoder
version, SparseIndex version, retrieval config, dataset version and timestamp. Query-boundary
diagnostics must distinguish that the encoder limit affects dense and hybrid while BM25 does not use
it. **Do not fabricate metrics.**

Do not invent a hard production quality threshold yet; M5 establishes a measured baseline. But do
not declare M5 satisfactory merely because the code runs, and do fix obvious implementation defects.

**Do not tune** `k1`, `b`, the RRF constant, weights, the analyzer or the candidate budgets merely
to make the synthetic benchmark look better. If a real defect is found, fix the defect and document
before/after. Synthetic Recall@5 = 1.000 is not proof of medical reliability.

## Testing, security and documentation

Unit tests for the query encoder (pinned revision, checksum, tokenizer, pooling, dimension, maximum
input, finite vectors, same-host determinism, batch/single tolerance); dense retrieval (active
index, tenant filter, top-K, chunk identity, stale index exclusion, dimension, DOT semantics); BM25
(exact terms, biomedical identifiers, drug names, numbers and units, analyzer version, chunk
identity, tenant isolation, stale index exclusion); RRF tested mathematically against fixed
rankings; hybrid corpus-version mismatch and provenance; and the metric implementations. Integration
tests must drive the real path from upload through both indexes to retrieval with provenance and no
generation. Failure tests must cover encoder missing or mismatched, query too long, Qdrant
unavailable, sparse unavailable, corpus mismatch, interrupted build, duplicate task, stale run,
tenant mismatch, no relevant result and hydration failure. Frontend and browser tests must cover the
Retrieval Inspector, mode switching, ranks and scores, provenance navigation, errors, unauthorized
access, and the absence of any answer or confidence UI. Repeat M4's numerical discipline in a
host/container query-vector comparison and do not overstate determinism.

Security is mandatory: authenticated user, tenant-scoped active index, tenant filters in both lanes,
server-side hydration authorization, never a client-supplied tenant id, and never a cross-tenant
query filtered afterwards. Do not log full medical queries by default.

Update `docs/architecture/{retrieval,sparse-retrieval,data-model,deployment}.md` and
`docs/evals/retrieval-evaluation.md`, add an ADR for the query encoder, analyzer, RRF and
active-index compatibility policy, and create `docs/verification/m5.md` with the exact measured
results, known limitations, Git status and confirmation that M6 was not started.

## Stop condition

After M5 verification, **stop**. Do not start M6. Do not implement cross-encoder reranking, a BGE
reranker, ColBERT, context or parent/neighbour expansion, an evidence sufficiency gate, OpenAI,
Claude, answer generation or medical chat. Wait for explicit authorization.

Priority: **true evidence recall > tenant safety > corpus version consistency > reproducibility >
precision > latency.**
